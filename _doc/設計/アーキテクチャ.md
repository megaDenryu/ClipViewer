# ClipViewer のアーキテクチャ

本文書は、ClipViewer の層と依存の向き(何が何を知ってよいか)と、主要な設計判断を定める。
実装と食い違ったときは、どちらが正しいかを決めて一致させる。

## 1. 目的

ClipViewer は、1本の動画から切り出した短い区間(クリップ)を並べ、繰り返し・クロップ・次へ進む条件を付けて再生する
デスクトップアプリである。この系が成立させることは次の3つである。

1. 短い区間の繰り返しを、継ぎ目で途切れずに再生する。映像だけでなく音も、継ぎ目で途切れず雑音を出さずに鳴らす
2. ローカルの動画ファイルを、ファイルのパスで直接開く
3. クリップの並びを JSON の設定ファイルに保存し、ブラウザ版 ClipViewer(v4.0 形式)と双方向で読み書きする
4. 作ったクリップスタックをアプリの中のライブラリへ名前を付けて保存し、一覧から開き直して見返し・編集する(`ライブラリ.md`)

## 2. 層の定義

矢印は「知ってよい」向きである。`clip_viewer` はすべてのクレートを知る。`video_source` と `audio_output` は `audio_pcm` と
`clip_domain` を知り、互いを知らない。`audio_pcm` と `clip_library` と `thumbnail_cache` は `clip_domain` だけを知る。逆向きの依存は無い。

```
clip_domain  <--  audio_pcm  <--  video_source  <--  clip_viewer
    ^                 ^                                  |  |
    |                 +---------  audio_output  <--------+  |
    +-------------------------  clip_library  <-------------+
    +-------------------------  thumbnail_cache  <----------+
```

| 層(クレート) | 何を持つか | 何を知ってよいか |
|---|---|---|
| `clip_domain` | クリップ・クロップ範囲・リピート・トリガー・再生モード・アスペクト比・時間の型。クリップスタックの操作、区間の端を動かす規則(`区間の編集の決まり`)、タイムライン上の位置で再生するものを求める処理、再生位置と再生の時計の規則、クリップの終わりで待つ規則、設定ファイル(JSON)の読み書き、スタックのライブラリの項目と形式(版ごとの型と最新への変換)、動画パスの検証、クロップ枠の移動と大きさの変更の計算、同時再生の重ね合わせ(`overlay/`。重ね合わせ・使う動画の表・置いたクリップ・クリップから受け継いだ値・タイムラインの行の並び・映す矩形・置いたクリップの音の設定・重ね合わせ上の時刻の型と、置く・動かす・映す矩形を変える・取り除く操作。設計は `同時再生.md`)、音量の型(`audio_pcm` が再公開する)、基準を型引数で分けた百分率(元の動画に対する・重ねる画面に対する)、小数を整数へ丸める計算(`as` を禁じた lint の下で `audio_pcm` と `video_source` も使う) | 何も知らない(serde / serde_json / thiserror だけに依存する) |
| `video_source` | FFmpeg を外部プロセスとして呼ぶ境界。動画の情報(長さ・幅・高さ・コマの速さ・読む映像の流れ・音の有無)の取得、裏のスレッドでの区間のデコード、1つの動画に結び付いたコマの倉庫(溜めたコマの予算の計上と、画面から渡された保持の優先順に従って捨てること)、流し読み、音の読み出し(音の倉庫と音の流し読み)、一覧のサムネイルの撮影 | `clip_domain` |
| `audio_pcm` | 音の値の型(サンプリング周波数・標本数・動画上の標本位置・小数の標本位置・標本の差・小数の標本の範囲・左右の標本と、その足し算・−1〜1 へ収める演算。音量は `clip_domain` の型を再公開する)と、音を受け渡す入れ物(溜めた音・流れてくる音)。音を作る側(`video_source`)と鳴らす側(`audio_output`)が同じ型で受け渡すための層である。FFmpeg の呼び出しも出力装置も持たないが、流れてくる音は書き手と読み手の錠と待ち合わせ(`Mutex`・`Condvar`)を持つ | `clip_domain`(時刻と時間の長さ)だけ |
| `audio_output` | 音声出力装置(cpal)を開く境界と、装置が音を求めるたびに次の標本を作る音の再生器(読み位置・映像とのずれの判定・継ぎ目の重ね合わせ・速度に合わせた読み方・音量)と、重ね合わせの行ごとの音の再生器の標本を足し合わせて −1〜1 へ収める行の音を混ぜる係と、それを同じ装置の2本目の流れで鳴らす `行を混ぜる音声出力`(判断8-9) | `clip_domain`・`audio_pcm`・cpal |
| `clip_library` | スタックのライブラリのフォルダの読み書き(一時ファイルへ書いてから置き換える)、一覧の走査と読めないファイルの報告、動画が見つからない判定、以前の版が置いたサムネイルの片付け、書き込みと走査を裏のスレッドで行う係、書けるアプリを1つに限る錠(起動の部分がウインドウを作る前に試せる。複数起動を妨げず、共有データへの書き込みだけを限る)。重ね合わせのフォルダ(ライブラリのフォルダの下の `overlays`)を同じ規則で読み書きし走査する係(`裏で動く重ね合わせのライブラリ`)と `overlays` の錠(ライブラリの錠を持つアプリだけが取る)。サムネイルを知らない。設計は `ライブラリ.md`、重ね合わせの部分は `同時再生.md` 4-2 | `clip_domain`・thiserror・std::fs だけ |
| `thumbnail_cache` | ライブラリの一覧と重ね合わせの一覧に出すサムネイルのキャッシュ(`%LOCALAPPDATA%\ClipViewer\thumbnails\`)。撮り方の要約値をファイル名にして JPEG を置く・読む・捨てること、容量の上限まで使った時刻の古いものから消すこと。複製したキャッシュは書き込みの錠を共有し、同じプロセスの中で置くことを1つずつ行う。設計は `ライブラリ.md` 判断10・判断11 | `clip_domain`・thiserror・std::fs だけ |
| `clip_viewer` | SengenEgui の画面、再生の時計の駆動、操作の応答の適用、アプリの設定、音の再生の指示の組み立て、各起動で独立したウインドウを作る手順と以前の版からの受け渡しの受信(この計算機の中だけの TCP。`画面.md` 判断13)、コンポジションルート | すべてのクレート |

`clip_viewer` の内側の層は `画面.md` 2節が正本である。そのうち見る側の設定の値の層(`clip_viewer` の `viewer_settings/`。ウインドウの大きさと最大化・音量・速度・左右の向き・キーの割り当て・
アスペクト比・表示サイズのように、次に起動したときへ持ち越す見る人の好みの値の型)は、状態(`state/`)と永続化境界(`persistence/`)の両方が使う。
`viewer_settings/` は `clip_domain`・`audio_pcm`・SengenEgui の寸法の型とキーの型だけを知り、`state/` も `persistence/` も知らない。
`persistence/` が `state/` を知らない向きを保ったまま、同じ値の型を settings.json と状態の両方で使うための置き場所である(`画面.md` 判断17)。

```
viewer_settings  <--  state
       ^
       +-----------  persistence
```

`video_source` は `clip_domain` を知ってよい。`clip_domain` は何も知らないので循環しない。`video_source` が使うのは
値の型(時刻・時間の長さ・画素の寸法・動画パス)であり、クリップスタックやタイムラインの規則には触れない。
この「規則には触れない」は Cargo では強制できないため、`video_source` の検収で確かめる。

境界の強制手段はクレートの分割(Cargo の依存)である。`clip_domain` の `Cargo.toml` に egui も FFmpeg の呼び出しも書かれて
いないため、`clip_domain` の中から画面やデコードを呼ぶコードはコンパイルできない。`video_source` の `Cargo.toml` に
egui を書かないことで、デコードの層が画面を知らないことも同じく強制する。cpal への依存は `audio_output` の `Cargo.toml` にだけ書き、
FFmpeg の呼び出しは `video_source` にだけ置く。`clip_library` と `thumbnail_cache` の `Cargo.toml` には `clip_domain` と thiserror だけを書き、ライブラリとサムネイルのキャッシュの読み書きが画面も FFmpeg も知らないことを強制する。`video_source` と `audio_output` は互いを依存に書かないため、音を作る側と鳴らす側は
`audio_pcm` の型だけを介して受け渡す。

## 3. 主要な設計判断

### 判断1: 収まる区間は先にデコードしてRAMに溜め、収まらない区間は流し読みする

ブラウザ版は、区間の終わりに達するたびに `<video>` をシークして区間の先頭へ戻していた。シークはキーフレームからの
デコードを伴うため時間がかかり、継ぎ目で映像が詰まる。本アプリは再生の経路からシークを外す。第3段階の実装員は、
本節だけを見て `video_source` を作れるようにする。

**1-1. 溜めるもの。** 溜めるコマは、表示用に縮めた元のコマ全体である。長辺の上限は設定値(既定1280画素)とする。
クロップはデコードの時点で掛けず、表示の時点で GPU の切り出しで掛ける(SengenEgui の口は判断5の末尾を参照)。
この形にするため、クロップを編集しても溜め直さずに済む。

**1-2. 画素の形式と見積もり。** 画素の形式は RGBA8(1画素4バイト)とする。溜める前に、必要なバイト数を
「コマ数 × 幅 × 高さ × 4」で見積もる。コマ数は、区間の開始を含むコマから、区間の終わりより前に表示が始まるコマまでの数で
あり、動画の終わりより後ろは数えない。幅と高さは長辺の上限へ縮めた後の寸法である。1280×720・30コマ/秒なら1コマ約3.7MB
(1280×720×4 = 3,686,400バイト)であり、RAMの上限の既定値2GB(2,000,000,000バイト)には約540コマ、約18秒分が収まる。
見積もりは倉庫が保持する動画の情報(元の寸法とコマの速さと長さ)から、デコードせずに即座に行う(`動画の情報::区間を見積もる`)。
見積もりの型 `区間の見積もり` は先頭のコマ・コマ数・縮めた寸法を持ち、バイト数はそこから求めるので食い違わない。
上限の扱いは 1-4 で決める。

**1-3. 非同期。** デコードは `video_source` が持つ裏のスレッドで行い、画面のスレッドを止めない。
- 「区間を溜める依頼」は即座に受付の札を返す。完了・失敗・進み具合は、画面が毎フレーム札で問い合わせる(待たない)
- 区間を続けて編集したときは、古い依頼を札で取り消せる。処理待ちなら待ち行列から外し、デコード中なら ffmpeg を止め、
  溜め終えていれば溜めたコマを捨てる
- 流し読みも裏のスレッドがコマを上限付きの通り道(bounded channel。詰まったら送り手が待つ通り道。容量4コマ)へ送り、
  画面はその時刻に出すコマを `その時刻に出すコマ` で取り出す。流し読みでシークするときは閉じて開き直し、FFmpeg を起動し直す
- 流し読みが持つコマは RAMの上限の予算の外である。通り道の4コマ、画面が取り出したコマと次のコマ、裏のスレッドが読み途中の
  1コマを合わせて、最大で約7コマである

**1-4. コマの倉庫。** 溜めたコマの管理(予算の計上と捨てること)は `video_source` の「コマの倉庫」が持つ。
- **倉庫は1つの動画に結び付ける。** 開くときに、動画の情報(正規化した動画パスと、ffprobe で調べた元の寸法・コマの速さ・長さ・読む映像の流れ・音の有無)・
  長辺の上限・RAMの上限を受け取って保持する。依頼・取り出し・破棄の口は動画のパスを受け取らない。
  別の動画を読み込んだら、画面は倉庫を作り直す。古い倉庫を落とすと、実行中の ffmpeg を止め、裏のスレッドの終わりを待つ
- **保持の優先順。** 画面は倉庫へ「保持の優先順」(区間の並び。先頭ほど残したい)を渡す。スタックや再生中の
  クリップが変わるたびに渡し直す。倉庫はクリップや再生の規則を知らず、渡された並びだけで、捨てる順と処理する順を決める
- **処理する順。** 裏のスレッドは次の依頼を選ぶたびに、その時点の保持の優先順で最も上位の処理待ちの依頼を選ぶ。
  優先順に無い依頼は受付順で最後に回す。実行中の依頼は、より上位の依頼が来ても途中で止めない
- **捨てる順。** 空きが要るときは、優先順に無い区間を先に捨て、次に優先順の後ろの区間から捨てる
- **上限の扱い。** 溜める依頼は次のどれかになり、受け付けない理由は型(`受け付けない理由`)で返す
  1. 同じ区間の依頼が既にあれば、その札を返す(溜め直さない)
  2. 区間の中で表示が始まるコマが無い(長さ0や動画の終わりより後ろ)区間は受け付けない(`区間にコマが無い`)
  3. 見積もりがRAMの上限の全体を超える区間は受け付けない(`上限の全体を超える`。画面はその区間を流し読みで再生する)
  4. それ以外は、優先順がその区間より低い区間(優先順に無い区間を含む)を捨てて空きを作り、受け付けて溜める
  5. 優先順がその区間以上の区間を捨てないと空きが作れないなら、受け付けない(`優先順の高い区間で埋まっている`)
  6. 裏のスレッドが異常終了していれば受け付けない(`裏のスレッドが止まっている`)
- 予約は受け付けた時点で見積もりの大きさを数え、処理待ち・デコード中・溜め終えたのどれでも同じ大きさで数える
- 区間の開始・終了を編集したら、画面がその区間の破棄を倉庫へ依頼し、新しい区間を溜める依頼を出す。
  溜め終わるまでの間は流し読みで表示する
- 溜めたコマを取り出す口は、コマとその動画上のコマ番号の組(`番号付きのコマ`)を返す。画面は番号を前のフレームと比べ、
  同じコマなら GPU へ載せ直さない。番号が同じなら同じ画像であるのは、同じ動画を同じ長辺の上限で読んだときだけである。
  区間の開始より前の時刻には最初のコマ、区間の終わり以降の時刻には区間の最後のコマを返す。
  末尾で止めたときに、`clip_domain` の `表示するコマを求める` が返す「最後のクリップの区間の終わり」を表示するためである
- 第4段階への申し送り: 画面は GPU へ載せ直すかを決める比較の鍵に、コマ番号に加えてコマの寸法と、動画を読み込み直したこと
  (倉庫や流し読みを作り直したこと)の区別を含める。番号だけでは、別の動画や別の長辺の上限のコマを同じとみなしてしまう
- ffmpeg が見積もりより少ないコマしか出さなかったときも失敗にしない。完了の状況(`溜め終えた内訳`)に実際のコマ数と
  見込みのコマ数を載せ、画面が知れるようにする
- 外れた依頼(失敗・取り消し・捨てた)の結末は直近1024件まで覚える。それより古い札は `知らない札` として答える
- 裏のスレッドからの報告は、倉庫の各操作の最初に取り込む。捨てた依頼の最後の報告は、次の操作で取り込まれて捨てられるまで
  通り道に残る(溜め終えたコマの並びなら、次の操作までの約1フレームの間 RAM に残る)

**1-5. 先読み。** 動画を読み込んだとき・スタックを変えたときに、画面が全クリップの区間を溜める依頼を
「再生中のクリップ → 次のクリップ → 残り」の順で出し、同じ順の並びを保持の優先順として倉庫へ渡す。
先読みで溜めただけの区間も優先順に載るので、再生中の区間の依頼のために先読みした区間が先に捨てられることはない。
利用者が別のクリップを選んだら、画面は優先順を渡し直す。裏のスレッドは次に選ぶ依頼からその順に従う。

**1-6. 型の置き場。** 「コマの速さ」「長辺の上限」「RAMの上限(`メモリの上限`)」「バイト数」「コマ数」「動画上のコマ番号」は
動画を読む側の値なので `video_source` に置く。デコードしたコマの寸法は整数の `コマの寸法` で持ち、`clip_domain` の
`画素の寸法` が要るときは `コマの寸法::画素の寸法へ変換する` で変換する。再生に使う動画のパスは `clip_domain` の
`正規化した動画パス` である(`検証済みの動画パス` は設定ファイルの書き出し専用)。時刻と区間は `clip_domain` の型を使う。

**1-7. 公開の口。** `video_source` の公開の口は次の形である。FFmpeg の引数や出力の形を公開面に出さない。
外の層が FFmpeg を使うときは、必ず `FFmpegの実行ファイル::探す` で見つけた実行ファイルから作る `動画の読み手` を通す。

| 口 | 受け取るもの | 返すもの |
|---|---|---|
| 動画の情報を取る | 正規化した動画パス | `動画の情報`(パス・動画の長さ(`時間の長さ`)・元の寸法(`コマの寸法`)・コマの速さ・読む映像の流れ・音の有無)。ffprobe を1回だけ呼び、終わるまで待つ。30秒の期限を過ぎたら ffprobe を止めて `時間切れ` を返す |
| 倉庫を開く | 動画の情報・長辺の上限・RAMの上限 | その動画に結び付いたコマの倉庫 |
| 保持の優先順を渡す | 区間の並び(先頭ほど残したい) | なし |
| 区間を溜める依頼を出す | 動画上の区間 | 受付の札(即座に返る。同じ区間の依頼が既にあればその札)。受け付けないときは 1-4 の理由 |
| 依頼の状況を問い合わせる | 受付の札 | 処理待ち・処理中(溜めたコマ数と見込みのコマ数)・完了(溜め終えた内訳)・失敗・取り消した・捨てた・知らない札の7つのどれか |
| 依頼を取り消す | 受付の札 | なし。溜め終えた依頼なら溜めたコマを捨てる |
| 溜めたコマを取り出す | 動画上の区間・動画上の時刻 | `番号付きのコマ`(コマ番号と RGBA8 のコマ)。区間の開始より前は最初、終わり以降は最後のコマ |
| 区間の破棄を依頼する | 動画上の区間 | なし |
| 流し読みを開く | 動画の情報・開始する動画上の時刻・長辺の上限 | `流し読み`。`その時刻に出すコマ` がコマ番号・表示の始まりの時刻・コマを返す。シークはこれを閉じて開き直す |
| サムネイルを作る | サムネイルの撮り方(動画のパス・時刻・クロップ範囲・大きさ)・取り消しの合図 | `サムネイルの画像`(JPEG のバイト列)。ffprobe で動画の情報を調べてから、再生と同じ規則(1-10)で時刻を含むコマを ffmpeg に撮らせ、終わるまで待つため、画面のスレッドから呼ばない。ffprobe は30秒、ffmpeg は10秒の期限を過ぎるか取り消されたら子プロセスを止めて失敗を返す。続けて撮るときは `撮影に使う動画の情報の覚え` で動画の情報を使い回す(`ライブラリ.md` 判断10) |

「倉庫を開く」と「流し読みを開く」と「サムネイルを作る」は `動画の読み手` のメソッドであり、「保持の優先順を渡す」から「区間の破棄を依頼する」までは
倉庫のメソッドである。倉庫の区間の見積もりは `倉庫.動画().区間を見積もる(区間, 長辺の上限)` で求める。

**1-8. 流し読みでの繰り返し。** 溜められない区間(上限の全体を超える区間、溜め終わる前の区間)を繰り返すときは、
区間の終わりで流し読みを閉じ、区間の開始から開き直す。開き直しはシークを伴うため、継ぎ目の詰まりは避けられない。
継ぎ目を途切れさせないのは溜めた区間だけである。

**1-9. 読む映像の流れ。** 動画の情報は、添付の画像(mp4 のカバー画像等)を除いた最初の映像の流れを調べ、その流れの番号(ffprobe の index)を持つ。
区間を溜める ffmpeg と流し読みの ffmpeg とサムネイルを撮る ffmpeg には `-map 0:<番号>` でその流れを読ませる。流れを指定しないと、
ffmpeg は既定の印や解像度で別の流れを選び、調べた寸法と読むコマが食い違う。
結合試験 `two_streams.rs` が、映像の流れが2つある動画で確かめる。

**1-10. 出力のコマとコマ番号の対応。** 溜めるときも流し読みも、ffmpeg の出力のi番目を動画上のコマ番号「先頭のコマ + i」とみなす。
この対応は、fps フィルタでコマの速さを一定にそろえ、丸めの境目をどのコマの時刻からも半コマ離して保つ(`コマを読む位置`)。
シーク位置を先頭のコマの始まりの半コマ手前にし(動画の先頭のコマは、シークせずに時刻へ半コマを足す)、fps フィルタは
切り捨て(`round=down`)で使う。mkv・webm はコマの時刻をミリ秒で持つため、元のコマの時刻が理想の時刻から前後にずれる。
丸めの境目をコマの時刻に置くと、丸めの向きがコマごとに変わり、コマが重複・欠落する(以前の四捨五入の形では、30コマ/秒の mkv で
確かめた132コマのうち36コマが食い違った)。結合試験 `numbering_store.rs`・`numbering_stream.rs` が、30・60・29.97コマ/秒の
mkv と webm で、付けたコマ番号とコマに描いた番号が合うことを確かめる。動画の終わりに届く区間と終わりまでの流し読みでも、最後のコマまで出ることを確かめる。
fps フィルタには、動画の種類によらず出力の始まりを0秒と教える(`start_time=0`)。シーク位置の直後にコマの無い時間があっても、
出力の0番目をシーク位置の枠に保つためである。コマの無い時間ができるのは、可変フレームレートの動画の隙間と、入れ物の始まりより
遅れて始まる映像(音が先に始まる動画)である。隙間の枠を埋めるコマは、読み始めの位置で変わる。読み始めが隙間の中なら隙間の後ろの
最初のコマで埋まり、読み始めが隙間より前なら隙間の前の最後のコマで埋まる(`numbering_gap.rs`)。遅れて始まる映像では、映像が
始まる前の枠を最初のコマで埋める(`numbering_late.rs`。ffmpeg 4.4.1 では、`start_time` を外しても ffmpeg の出力側の同期が同じように
埋めたため、この試験は `start_time` の有無を見分けない)。コマ番号は ffprobe の平均のコマの速さで数えるため、平均が元の刻みと違う動画
(隙間のある mp4 では平均が下がる)では、コマ番号は元のコマと1対1に対応しない。番号と時刻の対応は保たれる。表示するコマがその時刻に
映っているコマになるのは、固定フレームレートの動画と、読み始めより後ろにある隙間の枠である。読み始めが隙間の中なら、隙間の枠には
その時刻より後ろのコマが出る。

**1-11. 重ね合わせの供給。** 同時再生の重ね合わせの作業場(`同時再生.md`)は、使う動画の表の動画ごとに倉庫を1つ開き、同じ動画の
複数の置いたクリップの区間を1つの倉庫に溜める。流し読みとテクスチャはタイムラインの行ごとに1つ持ち(1つの行は同時に1つの置いたクリップしか
映さない)、行が何も映さない間は流し読みを閉じる。先読みの並びは、動画ごとに「今映している置いたクリップ → 時刻より後に始まる置いたクリップ →
残り」の順にし、1-5 と同じく同じ順を保持の優先順として渡す。倉庫と依頼の台帳と流し読みの開き直しの判断の規則は、1本の動画の画面と同じものを使う。台帳の手順を倉庫へ行う工程と、溜めたコマか流し読みから載せる工程も、
1本の動画の画面と同じ型を使う。`video_feed` の動画のコマの供給元(読み手・倉庫・依頼の台帳。台帳の手順を倉庫へ行う)を動画ごとに1つ、コマの載せ先(流し読み・テクスチャ。溜めたコマか流し読みから載せる)を行ごとに1つ持つ。1本の動画の画面の読み込んだ動画は、この2つを1つずつと動画の音を持つ(`同時再生.md` 3-3)。作業場を控えるときは、行ごとの流し読みを閉じる。
重ね合わせの作業場の倉庫は、スタックの作業場の倉庫と別に既定の上限(2GB)を持つ(`同時再生.md` 5-4 の既知の制約)。動画の読み手は、
重ね合わせを開くたびにスタックの作業場の動画の開き手から借りる。実装は `clip_viewer` の `overlay/feed/` である。

時計の1回の増分に上限を置く責務は、画面に持たせない。待つクリップを飛び越さないことは `clip_domain` の時計の規則
(判断6)が保証するためである。

### 判断2: FFmpeg は外部プロセスとして呼び、実行ファイルは設定の場所 → PATH の順で探す

FFmpeg をライブラリとしてリンクしない。外部プロセスとして `ffprobe`(動画の情報の取得)と `ffmpeg`(区間のデコード)を
呼び、標準出力から結果を受け取る。理由は2つある。unsafe の全面禁止と両立すること(リンクには FFI の境界が要る)と、
FFmpeg の実行ファイルが対応する動画の形式の網羅が広いことである。

実行ファイルは「設定の場所 → PATH」の順で探し、ffmpeg と ffprobe が同じフォルダにそろう最初の場所を選ぶ。
`clip_viewer` は設定の場所として、環境変数 `CLIPVIEWER_FFMPEG_DIR` があればそのフォルダを、無ければアプリの設定
(`%APPDATA%\ClipViewer\settings.json`)に保存したフォルダを渡す。環境変数があるときは保存したフォルダを探さない
(探す順は「環境変数 → 保存した設定 → PATH」であり、環境変数と保存した設定の両方を探すことはしない)。
版の違う組を選ばないため、2つを別々のフォルダから選ばない。どちらにも無ければ、探した場所を並べた型付きエラーで
明示し、黙って再生を諦めない。

結合試験を通して確かめた版は、ffmpeg 4.4.1(開発機)と 9.0.2(gyan.dev の essentials。GitHub Actions は choco で
この版に固定して入れる)である。ffmpeg と ffprobe へ渡す引数は、両方の版にある書き方だけを使う。版で書き方が変わった
ところは次のとおりである。
- サムネイルの JPEG は、フィルタの列の最後で画素の形式を全範囲の YUV(`yuvj420p|yuvj422p|yuvj444p`)に限る。
  9.0 は、コマが1つも来ないとき(時刻が動画の終わりより後ろ)に符号化器を狭い範囲の YUV で開こうとして異常終了するためである。
  限っても、コマがあるときの画像は両方の版で限らないときと同じである
- 試験の側では、時刻をそのまま残す指定(`-vsync 0`。9.0.2 は受け付けない。後継の `-fps_mode` は 4.4 に無い)を書かず、
  ffprobe の出力は csv でなく値だけを1行ずつ書く形(`default=nw=1:nk=1`)で読む。csv のコマの行は、9.0 が行末にカンマを足すためである

### 判断3: 設定ファイルはブラウザ版の v4.0 形式と互換にし、版ごとの型から最新へ変換する

設定ファイルの形はブラウザ版が書き出す v4.0 形式(`application: "ModifierVideoStack"`)と同じにし、どちらのアプリで
書いたファイルも他方で読めるようにする。`clip_domain` はファイル上の形をそのまま写した第4版の型(`settings/v4.rs`)を
持ち、読み込みでは版を判別してから最新の型(`スタック設定`)へ変換する。版が増えたときは、版ごとの型と最新への変換を
足し、最新の型へ互換の都合を持ち込まない。

欠けた項目(と null)の既定値はブラウザ版と同じである。名前は "Unnamed Clip"、有効、開始0秒、終了5秒、1回、
全体のクロップ、自動進行、識別子は新しく発行する。crop の中で欠けた項目は x=0・y=0・w=100・h=100 とし、
各値を範囲へ収める。ただし移植版は次の点でブラウザ版より厳しく、またはブラウザ版と違う。

- 次の設定ファイルを型付きエラーで拒む(ブラウザ版は黙って受け入れ、壊れた値のまま進んでいた)
  - 識別子が重複している
  - start が end より後ろにある
  - start か end が負か、数値でない
  - repeat が数値でも "infinite" でもない
  - triggerEvent が "none"/"Enter"/"Space"/"Click" のどれでもない
  - version が "4.0" でも欠けてもいない
- `"active": null` を欠けた項目とみなし、有効として読む(ブラウザ版は null を偽として扱い、無効として読んでいた)
- crop の各項目の null は欠けた項目とみなし、上の既定値にする(ブラウザ版は null で計算して値が壊れていた)
- 数値は秒・百分率を `5.0` の形で書き出す(ブラウザ版は `5`)。JSON の数値としては同じなので双方向で読める

書き出しは、クリップが1つ以上あること(`空でないクリップスタック`)と、動画パスが検証を通ったこと
(`検証済みの動画パス`)を型で要求する。どちらもブラウザ版が書き出しの前に画面側で確かめていた条件である。
書き出す expectedVideoName は、検証済みの動画パスが持つ「検証に使った期待する動画のファイル名」から取る。
ある名前で検証したパスを別の名前と組にして書き出すことはできない。

### 判断4: 部品を後から取る仕組みと、部品とハンドラの循環を持ち込まない

ブラウザ版は、部品(画面の要素)とハンドラ(操作の応答)が互いを参照し合うため、`ClipViewerApp依存` に「部品を後から取る
関数」を持たせて循環を切っていた。本アプリはこれを持ち込まない。egui は即時モード(毎フレーム、状態から画面を組み直す
方式)で描くため、部品が状態を保持し続ける必要が無い。画面は毎フレーム状態から組み直し、操作は「応答」の列挙として
集め、描画の後にまとめて状態へ適用する。これは SengenEgui の中核の方針と同じである。

### 判断5: 時間・割合・再生位置を型で分ける

ブラウザ版では「ビデオシーク秒」(元の動画の中の位置)と「仮想シーク秒」(クリップを並べた仮想の時間軸の中の位置)が
どちらも number であり、取り違えても型が通っていた。`clip_domain` は `時刻<基準>` に基準の型を持たせ、
`動画上の秒` と `タイムライン上の秒` を別の型にする。基準を持たない長さは `時間の長さ` で表す。
再生位置は再生モードごとの判別共用体 `再生位置`(シーケンス再生はタイムライン上の秒、単独クリップ再生は区間の開始
からの経過、元動画再生は動画上の秒)とし、時計を進める規則とモードの先頭へ戻す規則をこの型のメソッドに置く。
クロップの座標は元の動画に対する百分率(`百分率`、0〜100)、リピート回数は1〜100(`リピート回数`)の型で持つ。

SengenEgui の範囲枠付き画像は、ドラッグの移動量を割合の差(0〜1)で発する。`clip_domain` の `百分率の差分` は
0〜100 である。この変換は `clip_viewer` の境界1箇所(`view/conversion.rs`)で行う。

`clip_viewer` は SengenEgui を rev 8382d14 で取り込み、表示するコマを SengenEgui の `差し替えられるテクスチャ` に載せ、コマが変わったときだけ `差し替える` を呼ぶ。
出力とプレビューは使える大きさが分かってから組むため、`差し替えられるテクスチャ::参照を複製する()` で得た `登録したテクスチャの参照` を
`使える大きさから組む` の閉包へ所有させる。
クロップの表示は `画像(&参照).描く部分(割合で表した矩形).表示寸法へ引き伸ばす(寸法).押されたら発する(応答)`、
クロップ枠の編集は `範囲枠付き画像(&参照, 寸法, 枠, 応答の写像)`(占有は寸法に16論理画素を足した大きさ。
定数 `範囲枠付き画像の周りの余白`)を使う。`clip_viewer` の内側の設計は `画面.md` が定める。

### 判断6: 待つクリップは最後の周回を繰り返しながら待つ

クリップの終わりで待つクリップとは、無限ループか、トリガーが自動進行以外のクリップのことである(オーナーの決定)。
- 待つクリップは、回数指定なら最後の周回の終わりで、無限ループならどの周回の終わりでも、位置を1区間長戻して同じ
  周回を繰り返す。時計は止めない
- 1回の増分で待つクリップの終わりを越えたときは、進めた位置までに通る最初の待つクリップの最後の周回へ戻す。
  前の待たないクリップから一度に越える場合も、待つクリップを飛び越さない。全体ループが有効でも、最後のクリップが
  待つなら先頭へ戻らない
- 待ちは進める操作で解ける。トリガーを待たずに進める操作(画面の Next Clip・PageDown・Enter キーを写す)はどのクリップでも進める。自動進行の無限ループはトリガーを待たずに進める操作でだけ解ける
- 次へ進めるのはシーケンス再生のときだけである。次へ進む先は、再生できる(有効で区間の長さが0でない)クリップから選ぶ
- 最後のクリップで次へ進めたとき、全体ループが有効なら最初の再生できるクリップへ戻り、無効なら再生を止めて
  最後のクリップの最後のコマを表示する(オーナーの裁定)。時計が末尾で止まったときも同じである。
  タイムラインの末尾の位置はどのクリップにも当たらないため、表示するコマは `クリップスタック::表示するコマを求める`
  (末尾以降なら最後の再生できるクリップの区間の終わりを返す)で求め、画面にこの規則を作らせない
- シーケンス再生と元動画再生で、再生位置が合計の長さに達しているときに利用者が再生を押したら、モードの先頭から
  再生し直す(オーナーの決定)。末尾のまま再生を始めると時計がすぐにまた止め、再生が押せないように見えるためである。
  先頭へ移すかは `再生位置::再生を始める位置` が決める

ブラウザ版との差分は次のとおりである。
- ブラウザ版は無限ループを1周で次へ進め、トリガー待ちでは占有時間(区間の長さ×回数)ぶん巻き戻して最初の周回へ
  戻していた。この2つはオーナーの決定により移植しない
- 出力のクリックは、ブラウザ版でも周回に関係なくクリックしたときに次へ進めていた。Enterキー・Spaceキーの処理は
  ブラウザ版に無かった。本アプリの Enter キーは、トリガーを待たずに進める(オーナーの決定 2026-10-03)。Space は再生と停止に使うため、
  Space待ちは Enter待ちと同じく Enterキーで進む(`画面.md` 判断14)
- ブラウザ版は次へ進む先に長さ0のクリップを選んでいた。長さ0のクリップは再生できないので飛ばす
- ブラウザ版は最後のクリップで全体ループが無効なら次へ進める操作で何もしなかった。本アプリは再生を止める
- シーケンス再生と元動画再生で再生位置が末尾にあるときに再生を押すと、本アプリはモードの先頭から再生し直す(オーナーの決定)。
  ブラウザ版との差分である
- 単独クリップ再生は区間を繰り返す確認用の再生なので、合計は区間の長さとし、全体ループの設定に関わらず先頭へ戻る。
  合計の長さに達したときに0へ戻さず、周回の中の余りを保って戻す。継ぎ目を滑らかにするためであり、ブラウザ版
  (0へ戻す)との差分である。これはオーナーでなく統括役の指示による決定である

### 判断7: ドメインは表示の文字列を組み立てない

ブラウザ版のタイムライン上の位置で再生するものを求める処理は「Clip Mod 1 (2/3) [Trigger: Enterキー待ち]」のような表示の文字列を返していた。
`clip_domain` は、対象のクリップ・周回の状況・待っているかを構造化した値として返し、文字列は `clip_viewer` が組み立てる。
選択肢の値と型の変換(select 要素の "sequence" 等)も画面の都合なので `clip_domain` に置かない。例外は設定ファイルの
表記("none"/"Enter"/"Space"/"Click"、repeat の数値と "infinite")であり、これはファイル形式が決めているため
`settings/` の中で扱う。`clip_domain` の公開の型には serde_json の型を出さない。

### 判断8: 音は映像と同じ区間を溜めて鳴らし、音の再生器は映像の時計にずれたときだけ合わせる

第5段階で音を鳴らす。移植の動機は短い区間の繰り返しを継ぎ目で途切れさせないことであり、音も継ぎ目で途切れず、
雑音(プツッという音)を出さないことを成果物とする。

**8-1. 層。** 音の読み出し(FFmpeg で PCM を得ること)は `video_source` に置き、FFmpeg への依存を1つのクレートに閉じたままにする。
音声出力装置(cpal)への依存は `audio_output` 1つに閉じる。音を作る側と鳴らす側が受け渡す値と入れ物は `audio_pcm` に置く。
`clip_viewer` が、音の倉庫と音の流し読みを動画ごとに持ち、毎フレーム「再生の指示」を組み立てて `audio_output` へ渡す。

**8-2. 形式。** FFmpeg に `-vn -map 0:a:0 -ac 2 -ar <出力装置のサンプリング周波数> -f f32le` で区間の PCM を出させる。
出力装置のサンプリング周波数に合わせて FFmpeg が変換するため、アプリの中で周波数の変換をしない。
標本とは、ある1つの時点の左右の音の値の組のことであり、48kHz・2ch・f32 で1秒あたり約0.38MB(48,000×2×4 = 384,000バイト)である。
音があるかは、動画の情報を取る ffprobe の1回の呼び出しで、音の流れがあるかを見て決める(`動画の情報::音の有無`)。音の無い動画は「音が無い」として扱い、映像はそのまま再生して、再生コントロールに小さく出す。

**8-3. 溜める。** 音の倉庫は、映像の倉庫と同じく1つの動画に結び付け、動画を読み込み直したら作り直す。
古い倉庫を落とすと、映像の倉庫と同じく、読んでいる ffmpeg を落とす側から止め、裏のスレッドの終わりを待つ。
- 画面は、映像の先読みの並びと同じ区間の並び(再生中のクリップ → 次 → 残り)を、区間の集まりが落ち着いてから倉庫へ渡す。
  倉庫はその並びに無い区間をすぐに捨て、並びの順に上限(`音のメモリの上限`。既定は256,000,000バイトで、48kHz なら約11分)へ
  収まるところまでを溜め、収まらない区間は溜めない(流し読みで鳴らす)。裏のスレッドは並びの順に1区間ずつ ffmpeg で読む
- 映像の倉庫(判断1-4)より口を小さくした。音は1区間の読み出しが数十ミリ秒で終わり、上限も小さいため、札・取り消しを持たず、
  「溜める区間の並びを渡す」(`溜める区間の並びを渡す`)と「区間の状況を問い合わせる」(`区間の状況`。並びに無い・処理を待っている・
  読んでいる・溜め終えた・上限に収まらない・失敗のどれかであり、溜め終えていれば溜めた音を持つ)の2つと、倉庫を開いた溜め方を返す口(`溜め方`)で足りる
- 区間の開始より10ミリ秒前から溜める。継ぎ目で重ねる音を、区間の開始の手前から取れるようにするためである(8-5)
- 元動画再生と、溜め終える前の区間は、音も流し読みする。音の流し読みは、裏のスレッドが ffmpeg の出力を `流れてくる音`
  (4秒分の入れ物。鳴らし終えた位置より0.5秒前までを残し、それより古い標本の場所へ上書きする)へ書き足し、入れ物が埋まったら
  鳴らす側が進むのを待つ。開き直しの規則は映像の流し読み(`画面.md` 判断5)と同じであり、求める位置の0.1秒前から開く。
  開き直した直後は新しい入れ物がまだ空なので、新しい方に求める位置の標本が届くまで、開き直す前の流し読みを出どころとして渡し続ける。
  開き直す前の流し読みは、新しい方に届いたとき・新しい方が読めないか終わりまで読んだとき・前の方がその位置の標本を持たないときに閉じる
  (`clip_viewer` の `開き直しをまたぐ音の流し読み`)

**8-4. 鳴らす。** `audio_output` は既定の出力装置を既定の設定で開く。装置が音を求めるたびに呼ばれる関数(音声のスレッドで動く)は、
画面のスレッドが毎フレーム置き換える「再生の指示」(再生しているか・動画上の位置と指示した時刻・速度・音量・今の区間と
その出どころ・区間の終わりの行き先・位置を飛ばした回数)に従って、音の再生器で次の標本を作る。
- 指示と音の再生器は1つの小さな `Mutex` に入れる。画面のスレッドは中身を入れ替えるだけで錠を放し、古い指示は錠の外で捨てる
- 音声のスレッドで、メモリの確保・ファイル・FFmpeg の起動をしない。音の再生器が手放す溜めた音や流れてくる音(`Arc`)は
  固定の大きさの置き場へ移し、画面のスレッドが次のフレームで引き取って捨てる。最後の参照を音声のスレッドで捨てないためである
- 装置の標本の形式(f32 以外)とチャンネル数(2以外)は、この境界で変換する

**8-5. 映像との同期と継ぎ目。** 映像の位置は今までどおり `clip_domain` の時計が決める。
- 音の再生器は自分の読み位置を速度に従って進め、指示の位置を指示した時刻からの経過で進めた位置とのずれが40ミリ秒を超えたときだけ、
  読み位置を合わせる。区間を繰り返すときのずれは、区間の長さだけずらした候補も比べて最も小さいものを使う
- 区間の範囲は、秒から換算した端数のある標本位置(`小数の標本の範囲`)で持つ。音が区間を1周する長さを映像の1周(秒)と一致させ、
  無限ループで端数が周回ごとに溜まってずれにならないようにするためである
- 最後から2番目の周回から最後の周回へ移るとき、映像が先に最後の周回の頭へ入ると、行き先は「開始へ戻る」から「別の区間へ進む」へ替わる。
  映像が再生器より1周先にいる(読み位置の進みから映像の進みを引いた差が区間の長さの半分を超える)間は、行き先を置き換えずに
  今の周回を開始へ戻って交差させ、最後の周回を鳴らし切る。区間がずれの閾値より短くても、同じ周回の中の位置を1周先と取り違えない
- シーク・クリップの選択・モードの切り替えは、`再生の状況` の位置を移す操作が「位置を飛ばした回数」を1つ進め、音の再生器は
  回数が変わったら即座に合わせる。合わせるときと、停止・再開のときは、5ミリ秒で音量を0へ下げてから位置を移し、5ミリ秒で戻す
- 区間の終わりの行き先は `clip_domain` の `再生位置::区間の終わりの行き先` が決める(区間の開始へ戻る・別の区間へ進む・止まる)。
  音の再生器は区間の終わりで、行き先の位置へ読み位置を移す。区間の終わりの8ミリ秒は、行き先の手前8ミリ秒の音と重ねて交差させる
  (クロスフェード)。行き先の手前の音が無いとき(区間が動画の先頭から始まる・流し読みの途中)は、終わりの8ミリ秒で0まで下げ、
  行き先から5ミリ秒で戻す。止まるときと、行き先がまだ分からないとき(先に次の区間へ移った後、画面のスレッドが止まって次の指示が来ない間)は、
  終わりの8ミリ秒で0まで下げて区間の終わりで止まる
- 繰り返しの回数を終えて次のクリップへ進むときも、画面のスレッドが指示を置き換えるのを待たずに、音の再生器が行き先へ移る。
  行き先の規則は、時計の規則そのもので周回の終わりの少し先(丸めの許容誤差 `時間の長さ::丸めの許容誤差`。1マイクロ秒)まで進めて求め、時計と二重に書かない
- 位置の周回は、周回の始まりからの経過を区間の長さで割った正確な余りを先に引き、残りの整数に近い商を四捨五入して求める(`時間の長さ::周回番号を求める`)。
  商をそのまま切り捨てると、周回の境目の直前で商が丸めで整数へ上がったとき、余りが一周に近いのに次の周回を返し、周回と区間の中の位置が食い違うためである
- 読む標本が途切れたとき(流し読みの標本がまだ届かない・読み手が書き手に追いついた)は、最後に読めた標本を保ったまま5ミリ秒で0まで下げ、
  標本が戻っても0まで下げ切ってから5ミリ秒で上げ直す。途切れた波形と戻った波形の値が違うため、そのまま乗り換えると段差(雑音)になるからである

**8-6. 速度と音量。** 速度は、読み位置を1標本あたり速度の分だけ進め、間の値を前後の標本の線形補間で求める(音の高さも変わる)。
読み方は `速さを変える読み方` の実装として分けてあり、音の高さを保つ読み方(時間伸縮)へ差し替えられる。音量(既定0.5)は標本に掛け、0で無音にする。

**8-7. 出力装置が無いとき。** 装置が無い・開けないときは、型付きのエラー(`音声出力のエラー`)を画面の通知と再生コントロールに出し、
音の倉庫を開かずに映像だけで続ける。再生の途中で装置が使えなくなったとき(抜いたとき等)は、cpal の知らせを受けて
`音声出力のエラー::使えなくなった` を出し、アプリは止めない。使えない間に開く動画では音の倉庫を開かない(動画の開き手は開く時点の
音の出力の状況から周波数を受け取る)。

**8-8. 試験。** 音の再生器は装置から切り離した純粋な計算として単体試験する(継ぎ目の交差の区間で、出した標本が元の2つの波形の
重み付き和と一致すること・標本の途切れで段差を作らないこと等)。
装置を使う確認は `audio_output` の例(`examples/device_check/`。1本目と2本目の流れを開く。8-9)として置き、`cargo xtask verify` が最後に実行する。
装置が無ければ例は決まった終了コードで終わり、verify は「音声出力装置の確認を実行しなかった」と表示して最終行でそれを明示する。

**8-9. 行の音を混ぜる係と2本目の流れ。** 重ね合わせの作業場の音(`同時再生.md` 5-3)は、同じ既定の装置に開く2本目の流れで鳴らす。
1本目の流れ(スタックの作業場の `音声出力`)の型・公開の口・`再生の共有` の中身は変えない。
- `audio_output` の `行の音を混ぜる係` は、同時に重ねられる行の数(`clip_domain` の定数。8)だけの音の再生器と、行ごとの退いた出どころの置き場(今の32枠の型を8つ)と、
  1つの下書き(4096標本。約64KB。行ごとに順に貸して使い回す)を作るときに確保して持つ。下書きの標本数は `draft_size.rs` に置き、`mixer` は `device` を知らない。
  出力の長さは下書きの標本数以下であることを前提とし(音を埋める係が分けて渡す)、長い出力は到達したらバグとして止める。行ごとの再生の指示(`行ごとの再生の指示`)で各行の標本を作り、行の番号の順に
  `ステレオの標本::足す` で足し合わせ、`ステレオの標本::負の1から1へ収める`(`audio_pcm`)で −1〜1 へ収める。行の音量は今の再生器と同じく指示の音量を標本に掛ける
- 音を埋める係(`device/callback.rs`)は、時刻を受け取って並びを埋める共有(`時刻を渡して埋めさせる共有`)を型の引数で受け取る。1本目は `再生の共有` を、
  2本目は `行の音の共有`(行ごとの再生の指示と行の音を混ぜる係を1つの錠に入れたもの)を持つ。型の引数にしたため、1本目の流れの関数は今と同じ形に組み立てられ、
  装置の並びを埋める本体とチャンネルへ写す処理は1行も変えていない。回帰試験(c)の見本は書き換えずに通る
- 装置を開く手順(`device/stream.rs`)は、既定の装置と設定を選ぶこと(`選んだ装置`)と、共有を持たせて流れを始めること(`開いた流れ`)に分け、2つの出力が同じ手順を使う
- 2本目の流れの公開の口は、`音声出力` に型の引数を足さず、別の型 `行を混ぜる音声出力` にした。`音声出力` の公開の口と、それを使う `clip_viewer` のコードを変えないためである。
  口は `既定の装置を開く`・`周波数`・`指示を渡す`(`行ごとの再生の指示` を受け取る)・`使えなくなった理由`・`埋めた標本数` であり、`音声出力` と同じ形である
- 開く時期は、起動のときでなく、重ね合わせの作業場へ初めて移ったときにする(第11段階で配線する)。起動のときに開くと、重ね合わせを使わない利用者にも起動の時間と
  2本目の流れの音声のスレッドの負荷がかかるためである。開けないことを知るのは利用者が重ね合わせの作業場へ移った時点になり、その作業場の知らせにすぐ出せる。
  一度開いた流れは、スタックの作業場へ戻っても閉じず、止めている指示で黙った標本を出し続ける(開き直しの時間を作業場を移るたびに払わないため)。
  第11段階で `clip_viewer` の配線(`app/overlay_side.rs` の重ね合わせの側が持つ `重ね合わせの音の送り手`)へつないだ。画面のスレッドで開き(開発機で約5ミリ秒)、
  スタックの作業場が前の間も毎フレームどの行も黙る指示を渡して、行ごとの置き場の出どころを画面のスレッドで捨てる(`同時再生.md` 5-3)
- 開けないときは、`行を混ぜる音声出力::既定の装置を開く` が `音声出力のエラー` を返す。使っている途中で使えなくなったときは `使えなくなった理由` が返す。
  どちらも1本目の音の出力の状況とは別の値であり、第11段階で重ね合わせの作業場の音の様子と知らせに出す。黙って失敗させない
- `音声出力` と `行を混ぜる音声出力` は、流れ(`開いた流れ`)を共有より前の項目に置く。Rust は宣言の順に落とすため、先に流れを止めて音声のスレッドの関数が持つ参照を手放させ、
  共有の最後の参照を画面のスレッドで捨てる(8-4 の規則)。`開いた流れ` も cpal の流れを装置の知らせより前に置く。順は型の `注意:` に書いた
- 装置の知らせ(`device/notice.rs`)は、使えなくなった理由に加え、cpal が音の途切れ(`ErrorKind::Xrun`)を知らせた回数を数え、2つの出力が `途切れを知らされた回数` で返す。
  数えるだけで標本は変えない。注意: cpal 0.18 の WASAPI(Windows)は出力の流れで途切れを知らせない(入力の流れでだけ知らせる)ため、Windows では常に0である
- 例 `device_check` は、2本目の流れで8行に符号を反転した三角の波を交互に音量1で鳴らす。行の番号の順に足すと標本ごとにちょうど打ち消し合って0になるため、
  8行の再生器に音量0でない標本を作らせる負荷をかけながら、装置から音を出さない(`mixer/tests/cancel.rs` で確かめた)。確かめるのは、2本とも開けて音を求めること、
  2本目を開いている間に1本目の途切れを1回も知らされないこと、1本目の毎秒の埋めた標本数が1本だけのときの9割を下回らないことである。WASAPI は遅れた分を
  まとめて求めるため、埋めた標本数で捕まえられるのは大きく求められなくなったときだけであり、途切れの知らせは Windows では届かない。そのため Windows では、
  2本が同時に開いている間の短い途切れは機械では確かめられていない。開発機(48kHz)では1本だけで毎秒47,983標本、2本で毎秒47,997標本、途切れの知らせは0回だった

## 4. この段階でやらないこと

- **音の高さを保った速度の変更(時間伸縮)**: 速度を変えると音の高さも変わる。高さを保つ処理は、短い区間の繰り返しという
  主目的に要らず、実装の費用(位相を合わせた重ね合わせ等)が大きい。読み方を `速さを変える読み方` として分けてあるため、後から差し替えられる
- **出力装置の選択と、抜き差しへの追従**: 既定の出力装置だけを使う。途中で使えなくなったら知らせるだけで、開き直さない。
  開き直すには、出力装置を開く口をもう一度呼ぶ操作を画面へ足せばよい
- **流し読みの区間の繰り返しの継ぎ目**: 溜め終える前の区間を繰り返すと、映像と同じく開き直しで詰まる。音は開き直す前の流し読みに
  戻り先の標本が残っていればそれで鳴らし、無ければ下げて黙り、新しい流し読みに標本が届いてから上げ直す(途切れはするが段差は作らない)
- **動画ファイルへの書き出し(エンコード)**: ブラウザ版にも無い機能であり、移植の範囲に入らない。作らない
- **ブラウザ版以外の設定ファイルの版**: v4.0 形式しか存在しないため、他の版の型は作らない
- **Enterキー・Spaceキーの入力の受け取り**: ブラウザ版には処理が無かった。進める規則(`進める操作`)は `clip_domain` に
  置き、キー入力をこの操作へ写すのは `clip_viewer` である(Enter キーはトリガーを待たずに進める操作へ写す。`画面.md` 判断14)
- **再生の時計の毎フレームの駆動**: 時計を進める純粋な規則は `clip_domain` に置いた。毎フレーム実時間の経過を測って
  規則を呼ぶ駆動は、第4段階で `clip_viewer` に置く
