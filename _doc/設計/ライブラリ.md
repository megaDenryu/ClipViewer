# スタックのライブラリの設計

本文書は、編集したクリップスタックをアプリの中へ保存し、いつでも一覧から開き直して見返し・編集できるようにする仕組み(スタックのライブラリ)の、
層と依存の向き・保存の形式・保存の流れ・一覧の画面を定める。あわせて、同じフォルダに置くアプリの設定(settings.json)の形式と、両方の形式の版を上げる手順と、
公開した版から変えない互換の約束を定める(6〜8節)。クレートどうしの層の正本は `アーキテクチャ.md` であり、本文書はライブラリに関わる部分だけを扱う。
実装と食い違ったときは、どちらが正しいかを決めて一致させる。

## 1. 目的

スタックのライブラリとは、クリップスタックを名前を付けてアプリのデータのフォルダへ保存し、一覧から開き直せるようにしたもののことである。
オーナーの要望から、次の3つを成立させる。

1. 作ったスタックを保存し、アプリを閉じて開き直しても一覧から開いて見返し・編集できる
2. 保存するのは「どの動画のどこを切り抜くか」の情報だけにする。動画を切り抜いたり写したりしない。
   1つのスタックのファイルはクリップ10個で約2KBであり、クリップをいくつ作っても動画の容量は増えない。見るときは実行時に動画から読む。
   ライブラリには画像を置かない。一覧に出すスタックの顔(サムネイル)は、ライブラリの外の捨ててよいキャッシュに置く(判断10)
3. 同じ動画から複数のスタックを作れる。保存したスタックはこのアプリからだけ閲覧できればよい(ほかのアプリとの互換は、ブラウザ版の v4.0 形式の読み書きで別に保つ)

## 2. 層の定義

矢印は「知ってよい」向きである。

```
clip_domain  <--  clip_library     <--  clip_viewer
clip_domain  <--  thumbnail_cache  <--  clip_viewer
```

| 層(クレート) | 何を持つか | 何を知ってよいか |
|---|---|---|
| `clip_domain` の `library/` | ライブラリのスタック(項目)・スタックの識別子・スタックの名前・ライブラリの日時・形式の版ごとの型と最新への変換・ブラウザ版の設定(v4.0)からの取り込み・サムネイルの撮り方と大きさと画像の型。ライブラリの重ね合わせ・重ね合わせの識別子・重ね合わせの名前と、重ね合わせのファイルの版ごとの型と最新への変換(`同時再生.md` 4-2)。ファイルを知らない | `clip_domain` の中だけ(serde / serde_json / thiserror) |
| `clip_library` | ライブラリのフォルダの読み書き(一時ファイルへ書いてから置き換える)、一覧の走査と読めないファイルの報告、動画が見つからない判定、名前の変更・複製・削除・動画の場所の変更、以前の版が置いたサムネイルの片付け、書き込みと走査を裏のスレッドで順に行う係。重ね合わせのフォルダ(`overlays`)の同じ読み書きと走査と、それを裏のスレッドで行う係(`裏で動く重ね合わせのライブラリ`)と `overlays` の錠。名前の規則と書き込みの手順(`item_folder.rs`)と錠のファイルの取り方(`lock_file.rs`)と裏のスレッドの手順(`background_threads.rs`・`background_worker.rs`)は、スタックと重ね合わせが共に使う。サムネイルを知らない | `clip_domain` と std::fs・std::thread だけ。egui / SengenEgui / FFmpeg を知らない |
| `thumbnail_cache` | サムネイルのキャッシュ(撮り方から決めたファイル名で JPEG を置く・読む・捨てる・容量の上限まで古いものから消す) | `clip_domain` と std::fs だけ。egui / SengenEgui / FFmpeg / `clip_library` を知らない |
| `video_source` | サムネイルを撮る口(`動画の読み手::サムネイルを作る`。FFmpeg に1コマの JPEG を作らせ、期限を過ぎたら止める) | `clip_domain`(サムネイルの撮り方と画像の型) |
| `clip_viewer` | ライブラリとキャッシュの置き場所の決定、開いているスタックと自動保存の見張り、一覧の画面と操作の応答、開くときの動画の読み込み、サムネイルを撮る・読む裏のスレッドと、いつ何を撮るかの判断と、見えている行のテクスチャ(`thumbnail_feed/`) | すべて |

境界は Cargo の依存で強制する。`clip_library` の `Cargo.toml` には `clip_domain` と thiserror だけを書き、egui も video_source も書かない。
`thumbnail_cache` の `Cargo.toml` にも `clip_domain` と thiserror だけを書く。`clip_domain` の `Cargo.toml` は変えない(ファイルを読む口を持たない)。
サムネイルの撮り方(スタックの顔をどのコマからどの大きさで撮るか)とサムネイルの画像(JPEG のバイト列)の型は `clip_domain` に置き、`video_source`(撮る)と `thumbnail_cache`(置く)が同じ型で受け渡す。

## 3. 主要な設計判断

### 判断1: 保存するものは名前・動画のパス・クリップの並び・日時・版・識別子だけにする

1つのスタックのファイルに書くのは、形式の名前と版・スタックの識別子・名前・動画の絶対パス(正規化した動画パス)・作った日時・更新した日時・
クリップの並び(各クリップの識別子・名前・有効か・区間・繰り返し・クロップ・トリガー)である。クリップの選択中や再生位置・出力の設定は保存しない。
開いたときは先頭のクリップを選び、今の再生モードの先頭から再生する(動画を開いたときと同じ)。

一覧に出す「クリップ数」と「合計の長さ」は保存せず、読んだクリップの並びから求める。保存すると中身と二重に持つことになるためである。
合計の長さとは、全クリップの区間の長さの和のことである(繰り返しの回数は掛けない。無限ループのクリップがあると再生の長さが決まらないためである)。

### 判断2: 置き場所は `%APPDATA%\ClipViewer\library\` で、スタック1つにつき1ファイルにする

- フォルダ名は ASCII の `library` にする。同じフォルダの `settings.json` と揃え、ほかの道具で開くときに文字コードで困らないためである
- ファイル名は `<スタックの識別子>.json` である。名前は中身に持ち、名前を変えてもファイル名は変えない。識別子は `stack-<ミリ秒>-<0〜9999の乱数>` の
  形の英小文字・数字・ハイフンだけからなる文字列であり、ファイル名に使えない文字を含まない(`スタックの識別子::文字列から作成する` が検査する)
- 置き場所は `clip_viewer` が決めて `clip_library` へ渡す(試験は一時フォルダを渡す)。環境変数 APPDATA が無いときはライブラリを使えないものとし、
  起動は止めず、ライブラリの操作をしたときに理由を通知する
- ライブラリのフォルダの直下にはスタックのファイルと錠のファイルだけを置く。サムネイルは置かない(判断10)
- 重ね合わせのファイルは、ライブラリのフォルダの下のサブフォルダ `overlays` に、`<重ね合わせの識別子>.json` の1つ1ファイルで置く。`overlays` の中には重ね合わせのファイルとその書きかけ(`<識別子>.json.tmp`)と錠のファイル(`ClipViewer.lock`)だけを置く。
  書き込み・走査・読めないファイルの扱い・置き去りの書きかけの片付けは、スタックのファイルと同じ規則(本判断と判断3・判断6)を `overlays` に当てる。重ね合わせの識別子は `overlay-<ミリ秒>-<0〜9999の乱数>` の形で、スタックの識別子と同じ文字の規則で確かめる(`同時再生.md` 4-2)
- `overlays` の錠は、ライブラリのフォルダの錠を持つアプリだけが取る(`clip_library` の `重ね合わせのフォルダ::錠を取る` はライブラリの錠を借りて受け取る)。ライブラリの錠を取れなかったアプリは `overlays` の錠を取りに行かず、重ね合わせも読み取り専用で開く(判断9)。
  アプリを閉じるときは、`overlays` の錠をライブラリの錠より先に放す
- 書き込みは `<識別子>.json.tmp` へ書き、`sync_all` で記憶装置まで書き切ってから、`std::fs::rename` で `<識別子>.json` を置き換える。
  Windows の rename は既存のファイルを置き換える。書いている途中でアプリや電源が落ちても、元のファイルは壊れず、書きかけのファイルが残るだけである。
  書きかけのファイルは次に同じスタックを保存したときに上書きされる。スタックを削除するときは、そのスタックの書きかけも一緒に消す。ほかの理由で置き去りになった書きかけは、書けるアプリが走査の前に消す(判断3)。ほかのプロセスがスタックのファイルを排他で開いていて置き換えられないときは、
  失敗として返し、判断5の頼み直しに乗せる

### 判断3: 索引のファイルを作らず、一覧はフォルダを読んで作る

索引を置くと、索引と中身の二重管理になり、食い違いの直し方を決めなければならないためである。
一覧は、起動時と、一覧の画面を開いたときと、登録・取り込み・名前の変更・複製・削除・動画の場所の変更を頼んだ後に、フォルダの `*.json` をすべて読んで作る。
変更の後の読み直しは、変更と同じ裏のスレッドへ変更の後ろに頼むため、変更の後の中身になる。自動保存の後には読み直さない(一覧の画面を開くときに読み直すため)。

- 走査は裏のスレッドで行い、画面のスレッドを止めない。400件の走査は試験で時間を測り、5秒未満であることを確かめる(`clip_library` の試験。件数に対して急に遅くなる実装を捕まえるための上限であり、ウイルス対策が読むファイルを検査する環境では正しい実装でも約2秒かかる)
- 走査の対象はフォルダの直下の、拡張子が `json` のファイルだけである。書きかけのファイル(`.json.tmp`)とほかの拡張子のファイルとサブフォルダは、スタックのファイルでないため対象外とし、サブフォルダの中は読まない(8節「互換の約束」)
- 対象のファイルが読めない・形式が壊れている・版が新しすぎる・ファイル名と中身の識別子が違うときは、一覧に「読めない(理由)」の行として出す。黙って飛ばさない。
  読めないファイルには、ライブラリの操作(名前の変更・複製・削除・保存)で触れない
- 各項目について、動画のパスにファイルがあるかを走査のときに確かめ、無ければ「動画が見つからない」の印を付ける
- 書けるアプリ(判断9)は、一覧を作る前に、以前の版がライブラリのフォルダに置いたサムネイル(`*.jpg` と `*.jpg.tmp`)を消す(判断10)。
  あわせて、対応するスタックのファイルが無く、最後に書き換えてから1日より古い書きかけのファイル(`<識別子>.json.tmp`)を消す。
  初めて保存するスタックでは、置き換え(rename)に失敗するとスタックのファイルが無いまま書きかけだけが残り、それが唯一の写しになる。
  1日待つのは、その写しを利用者が拾い出す時間を残すためである。置き換えに失敗したときの理由の文には書きかけのファイルのパスを入れ、利用者が場所を知れるようにする。削除したスタックの書きかけは、削除のときに一緒に消すため、この片付けを待たない。
  片付けは書き込みのスレッドが書き込みと順に行い、錠が書けるアプリを1つに限るため、書いている途中の書きかけを消すことは無い。
  対応するスタックのファイルがある書きかけは、次の保存で上書きされるため残す
- 裏のスレッドが止まっていて一覧を作る頼みを送れないときは、一覧を読めないとして一覧の画面に理由を出す(古い一覧を黙って見せ続けない)。
  置き場所が無いときは置き場所の文で知らせているため、一覧の読み直しでは重ねて知らせず、一覧の本体(「一覧を読んでいる」等)も出さない

### 判断4: 形式は版を持つ新しい形式にし、版ごとの型から最新へ変換する。v4.0 は残して取り込める

ライブラリのファイルは、ブラウザ版の v4.0 形式ではなく新しい形式(第1版)にする。v4.0 には識別子・名前・作った日時・更新した日時が無く、
version が文字列で、欠けた項目を既定値で補う取り決めがあるためである。

- 第1版の形は `clip_domain` の `library/v1.rs` がそのまま写す。読み込みは、先に `format` と `version` だけを読み、版に合う型で読んでから
  最新の `ライブラリのスタック` へ変換する。版が増えたら版ごとの型と最新への変換を足し、最新の型へ互換の都合を持ち込まない(グローバル規約)
- 書き出しは常に最新の版で行う。JSON は空白を入れずに書く(容量を小さくするため)。日時は協定世界時の1970年1月1日からのミリ秒の整数で書く
- 第1版は欠けた項目を許さない。このアプリだけが書く形式であり、欠けていれば壊れたファイルである
- 第1版は知らない項目も許さない(`v1.rs` の3つの型の `deny_unknown_fields`)。項目を足した新しい版のファイルを古いアプリが読み、
  自動保存で足した項目を黙って消すことを防ぐためである。このため、スタックのファイルに項目を足すときは必ず版を上げる(7節)
- 版が新しすぎる(このアプリが知っている最新の版より大きい)ファイルは、「このアプリより新しい ClipViewer で保存された。ClipViewer を
  更新すれば開ける」を理由とする読めない行にする。version が無いか 0 のファイルは「読めない版」とし、2つを分ける
- 版ごとの型と最新の型の変換は、両方向とも最新の型を `..` を使わずに分解・組み立てる。クリップは `クリップの各項目`(`clip/parts.rs`)を通す。
  クリップやライブラリのスタックに項目を足すと、変換を直すまでコンパイルが通らないため、足した項目を書き忘れることが無い
- 日時は9999年12月31日(協定世界時)までに限る。ファイルの日時がそれより後なら、異常終了せずに読めない行にする(表示の変換で溢れないため)
- 重ね合わせのファイル(`format` が `ClipViewer.overlay`)も同じ方針で読み書きする。第1版の形は `clip_domain` の `library/overlay_v1.rs` がそのまま写し、欠けた項目も知らない項目も許さない。
  読み込みは見出しで版を判別してから第1版の型で読み、値を重ね合わせの部品一式(`重ね合わせの部品一式`)へ変換し、`重ね合わせへ組み立てる` で重ね合わせの不変条件(行の数の上限・行の中の時間の重なり・識別子の重なり・動画の番号・区間の長さ)を全部確かめる。
  破るファイルは型付きのエラー(`重ね合わせのファイルの読み込みエラー`)で拒む。形式の例は `同時再生.md` 4-2、見本は `tests/fixtures/overlay_v1.json` である
- ブラウザ版の v4.0 形式の「JSON読込」「JSON保存」はそのまま残す。一覧の画面の「v4.0 JSON を取り込む」は、v4.0 の設定ファイルを読み、
  expectedVideoPath があればライブラリへ新しいスタックとして登録する(名前は JSON のファイル名から拡張子を除いたもの)。expectedVideoPath が無い
  ファイルは、どの動画のスタックか分からないため取り込まずに理由を通知する

保存の形式の例(実際には1行で書く。ここでは読めるように改行した):

```json
{"format":"ClipViewer.library","version":1,"identifier":"stack-1790000000000-42",
 "name":"サビの振り付け","videoPath":"D:\\動画\\練習.mp4",
 "createdAtMs":1790000000000,"updatedAtMs":1790000123456,
 "clips":[{"id":"mod-1790000000000-7","name":"Clip Mod 1","active":true,"start":12.5,"end":14.0,
           "repeat":"infinite","crop":{"x":10.0,"y":0.0,"w":50.0,"h":100.0},"trigger":"Enter"}]}
```

### 判断5: 最初の登録は利用者が名前を付けて行い、登録済みのスタックは編集のたびに自動で保存する

- 動画を開いてクリップを作っただけのスタックは未登録である。ヘッダーの「ライブラリに保存」で名前を入力して決定すると、最初の登録になる。
  試しに開いただけの動画が勝手に溜まらないためである。名前の初期値は動画のファイル名から拡張子を除いたものである
- 登録済みのスタックを開いている間は、クリップの並び(選択中を除く)が最後に保存を頼んだ並びと違えば、変わらなくなってから0.5秒後に保存を頼む。
  毎フレーム並びを比べる形にしたのは、クリップを変える操作が多く、操作ごとに保存の呼び出しを足すと取りこぼすためである。区間の帯のドラッグの間は
  クリップスタックを書き換えない(`画面.md` 判断11)ので、ドラッグの間は保存しない
- 書き込みは `clip_library` の裏のスレッドが順に行う。画面のスレッドは頼むだけで待たない
- 登録済みのスタックは「ファイルに書けたと分かっている並び」を持ち、保存が成功したと知らせを受けたときだけ進める。保存に失敗しても、書けていない並びを
  書けたものとして扱わない。失敗したら3秒の間隔を置いて、今の並びの保存を頼み直す(書けない状態の間に書き込みを繰り返し過ぎないため)
- 入力が無い間も、落ち着き待ちの終わる時刻と頼み直す時刻に合わせて描き直しを予約し、画面を進めて保存を頼む。裏のスレッドの返事を待つ間だけは
  約60回/秒で描き直す。保存できない状態が続く間に毎フレーム描き直さないためである
- 今のスタックが「未登録」か、登録済みなら「保存済み」「変更を保存待ち」「保存中」「保存に失敗(理由)」のどれかをヘッダーに出す。
  保存に失敗したときは、次の保存が成功するまで失敗を出し続ける。開いているスタックの自動保存の失敗は、頼み直すたびに通知を繰り返さないよう、ヘッダーだけで知らせる
- 登録と v4.0 の取り込みは、書き込みを終えた知らせを受けてから「保存しました」「取り込みました」を通知する(書けなかったのに成功を知らせないため)
- 開いているスタックの関係を終わらせる(未登録へ戻す)操作は、一覧から別のスタックを開く・動画の解除・別の動画を開く(並びを残さないとき)・今の動画で新しいスタックを始める・「JSON読込」・
  開いているスタックの削除である。どれも、そのまま自動保存を続けると、そのスタックを別の動画や別の並びで上書きしてしまうためである。
  同じ動画を開き直して並びを残すとき(`画面.md` 判断14)は、スタックの動画のパス全体が開く動画のパスと同じときだけ、上書きしないため関係を終えず、確かめもしない。
  ファイル名が同じでもフォルダが違えば別の動画かもしれないため、並びは残すが、保存を確かめてから関係を終える(スタックのパスは書き換えない。別の動画だったときにスタックを壊すため)
- 今の動画で新しいスタックを始める(`画面.md` 判断14)は、同じ動画から2件目のスタックを作るための操作である。登録済みのスタックで押すと、ほかの関係を終える操作と同じく
  保存を確かめてから関係を終えるため、元のスタックは最後の変更まで書けたままライブラリに残り、新しい並びは未登録として始まる。元のスタックを新しい並びで上書きしないためである
- 関係を終える操作のうち、動画を選んで開く・JSON読込は、ファイルを選ぶダイアログと読み込みを先に済ませてから確かめる(ダイアログを取り消したときに確かめるダイアログを出さないため)
- 未登録の並びの確かめは `画面.md` 判断14 が定める(並びを置き換えたときから変えていて、続ける操作が並びを捨てるときに「ライブラリに保存していない変更がある」のダイアログを出す。
  読み込んだ並びを名前の違う動画を開いて捨てるときもダイアログを出す)
- 削除以外の関係を終える操作とアプリを閉じる前は、今の並びが書けていなければ保存を頼み直し、書き込みを終えるまで待つ。それでも書けなければ
  「開いているスタックを保存できない(理由)。続けると、保存できていない変更が失われる」のダイアログを出し、[やめる] と [変更を捨てて続ける] を選ばせる。
  保存できない変更を黙って捨てないためである。[変更を捨てて続ける] は保存の確かめを飛ばして続ける操作を行い、関係はその操作が成功したときだけ終える
  (ファイルを選ぶダイアログを取り消した・スタックや動画を開けなかったときは関係を残し、頼み直しと閉じるときの確かめを続ける)。アプリを閉じるときは、起動の部分がウインドウを閉じる要求(`close_requested`)を受けて確かめ、書けなければ
  閉じるのを取り消し(`CancelClose`)、[変更を捨てて続ける] を選んだらウインドウを閉じる。確かめを経ずに落とされたときのため、アプリを落とすときにも
  書けていない並びの保存を頼み、裏のスレッドが頼まれた書き込みを終えるまで待ってから終わる

### 判断6: ライブラリへの書き込みは1本の書き込みのスレッドが順に行い、一覧の走査は別のスレッドで行う

保存・名前の変更・複製・動画の場所の変更・削除は、`clip_library` の `裏で動くライブラリ` へ頼みとして送り、1本の書き込みのスレッドが受けた順に行う。
名前の変更・複製・動画の場所の変更は、書き込みのスレッドがファイルを読み直してから変えて書く。順に行うため、自動保存と名前の変更が同じファイルを
取り合って片方が消えることがない。一覧の走査は走査のスレッドが行う。一覧を作る頼みは書き込みのスレッドを通してから走査のスレッドへ渡すため、
先に頼んだ変更の後の中身を読む。結果は知らせとして返り、画面のスレッドが毎フレーム受け取って、保存の様子と一覧を書き換える。

一覧から開くときだけは、画面のスレッドで1つのファイルを読む。読む前に、書き込みのスレッドが頼まれた書き込みを終えるまで待つ。
名前の変更の直後に開いたときに、変更前の中身を読まないためである。待つのは書き込みだけであり、一覧の走査(各項目の動画のパスの有無を確かめる。
ネットワークのドライブや眠っている HDD では時間がかかる)は待たない。書き込みの待ちは、書き込みの頼みが溜まっていなければ1ファイルの書き込み程度で終わるが、
書き込み先のドライブが遅ければその分だけ画面のスレッドを止める(関係を終える前の保存の確かめも同じ)。

### 判断7: 開くときは、未登録のクリップがあれば確かめ、登録済みなら変更を先に保存する

- 一覧の「開く」は、動画を既存の動画を開く経路(`動画の開き手`)で読み込み、クリップの並びを置き換え、開いているスタックをそのスタックにする。
  動画を開けなければ理由を通知し、今の画面は変えない
- 今のスタックが未登録で、並びを置き換えたときからクリップを変えているときは、「ライブラリに保存していない変更がある。続けると失われる」のダイアログを出し、
  [ライブラリに保存する] [変更を捨てて続ける] [やめる] を選ばせる。自動保存の対象でないため、黙って開くと失われるからである。動画を開いただけで作られる最初のクリップは
  変更に数えない(`画面.md` 判断14)
- 今のスタックが登録済みなら、落ち着くのを待っている変更をすぐに保存を頼んでから開く
- 開いたら編集の構えへ移る

### 判断8: 一覧の画面はヘッダーの構えの1つにする

ヘッダーの構えのボタン(編集・シアター)に「ライブラリ」を足す。ライブラリの構えでは、ヘッダーの下を一覧の画面にし、サイドバー・出力・再生コントロールを出さない。
一覧の画面へ移るときは再生を止める(映像が見えないまま音が鳴り続けないため)。

- 1件の行の左にサムネイルの枠(判断10)を出し、右に、名前・動画のファイル名・クリップ数・合計の長さ・更新日時(この計算機の時間帯で「2026-09-26 14:05」の形)・動画が見つからない印を出す。
  今開いているスタックの行には「開いている」を出す
- 名前で絞り込める(大文字と小文字を区別しない部分一致)。並べ替えは、更新日時の新しい順(既定)・更新日時の古い順・名前順・作った日時の新しい順である
- 操作は、開く・名前を変える(ダイアログで入力)・複製する(名前に「のコピー」を足す)・削除する(確認のダイアログ)・動画の場所を指定し直す(動画が見つからないときだけ出す。
  ファイルを選ぶダイアログで選ぶ)である
- 読めない行は、絞り込みと並べ替えに関わらず一覧の最後に、ファイル名と理由を出す
- 絞り込みと並べ替えの結果(見せる行の順)は、一覧を読み直したときと、絞り込みの語か並べ替え方を変えたときだけ作り直して状態に持つ(`並べた一覧`)。
  行は SengenEgui の仮想縦スクロールで、見えている行だけを組み、説明の文と日時の文も見えている行の分だけ作る。数百件でも毎フレームの費用が
  見えている行の数で決まり、全件の数に比例しないためである

### 判断9: 同じライブラリを書けるアプリは1つに限り、2つ目は読み取り専用にする

同じライブラリを2つの ClipViewer で開くと、一方の名前の変更や削除が、他方の自動保存で黙って上書きされたり蘇ったりする。これを防ぐため、
ライブラリのフォルダの錠のファイル(`ClipViewer.lock`。拡張子が json でないため一覧の対象にならない)を OS の排他の錠(`File::try_lock`)で開き、
アプリが生きている間持ち続ける。錠を取れた最初のアプリだけが書ける。

- 2つ目に起動したアプリは錠を取れず、ライブラリを読み取り専用にする。一覧の読み直しと一覧から開くことはできる。登録・自動保存・名前の変更・複製・削除・
  取り込み・動画の場所の変更は、`clip_library` の `裏で動くライブラリ` が書き込む頼みとして断り、画面はボタンを押せなくして理由を出す
  (ヘッダーに「ライブラリ: 読み取り専用」、一覧の画面に「別の ClipViewer がライブラリを開いている」)。読み取り専用で開いたスタックは未登録として開き、変更は保存しない
- 錠を持つアプリが落ちたときは、OS が錠を解く。錠のファイルは残るが、次に起動したアプリが開き直して錠を取れる
- 錠のファイルは起動時に作るため、ライブラリのフォルダは最初の保存の前(起動時)に作られる
- 起動の部分は、ウインドウを作る前に錠を試す(`錠を試したライブラリ`)。錠を取れなかったアプリも、自分のウインドウを作って引数の動画を開き、ライブラリを読み取り専用で使う。各アプリはほかのアプリへ動画を渡さず、複数の動画を別々に再生できる(`画面.md` 判断13)

### 判断10: 一覧の各行にスタックの顔のサムネイルを出す。サムネイルはライブラリの外の、捨ててよいキャッシュに置く

オーナーの要望(「ライブラリに保存したときはサムネ画像も取ってもらえるといい」)による。オーナーの考え方(「データは動画のパスとスタックのデータの最小限」)に従い、ライブラリにはサムネイルを置かない。サムネイルは、消えても撮り直せる派生のデータとして、ライブラリの外のキャッシュに置く。

- **撮るもの**: スタックの顔とは、最初の再生できるクリップの開始のコマに、そのクリップのクロップを掛けたもののことである。サムネイルの撮り方とは、動画のパス・開始の時刻・クロップ範囲・サムネイルの大きさの組のことであり(`clip_domain` の `ライブラリのスタック::サムネイルの撮り方`)、撮り方が等しければ同じ画像になる。再生できるクリップが無いか動画のパスが空なら撮らない
- **大きさ**: サムネイルの大きさとは、顔を縦横比を保って収める枠の、幅と高さの画素数のことである。一覧の枠(96×54 論理画素)の2倍の 192×108 画素にする。顔はこの枠に接するまで拡大か縮小する(小さいクロップは拡大する)。表示倍率が2倍までの画面で粗く見えず、JPEG を画素へ戻したものがそのまま枠の2倍の大きさになるため、戻した後に縮める工程が要らない
- **置き場所とファイル名**: `%LOCALAPPDATA%\ClipViewer\thumbnails\` に置く。LOCALAPPDATA は、ほかの計算機へ持ち回らない、この計算機だけのアプリのデータの置き場所である。ファイル名は、撮り方から求めた要約値を16進数32文字で書き、キャッシュの形式の版の印(`.v4` のように v と版の番号)と `.jpg` を付けたものである。撮り方の要約値とは、撮り方の各値(キャッシュの形式の版・動画のパスの文字列・時刻とクロップの各値の浮動小数点のビット列・大きさ)を決まった順にバイト列へ並べ、128ビットの FNV-1a の手順で混ぜて得る数のことである。同じ画像になる違いで別の名前にしないため、要約値を求めるときだけ値を揃える。Windows では動画のパスの区切り文字を `\` に揃えて小文字にし(Windows のパスは大文字小文字を区別しない)、どの環境でも -0.0 を 0.0 にする(ビット列が違うため)。動画を開くときのパスと `clip_domain` の正規化は変えない。std の `DefaultHasher` は Rust の版で結果が変わりうるため使わない。FNV-1a は手順と定数が公開されていて版で変わらず、依存を足さずに書ける。128ビットにするのは、数万件でも偶然の一致が起きる見込みを無視できる大きさにするためである(暗号学的な強さは要らない)
- **古いサムネイルが出ない理由**: 顔が変われば(最初の再生できるクリップの開始・クロップ・動画のパスのどれかが変われば)撮り方が変わり、別のファイル名になる。撮り方のファイルが無ければ撮る。このため、撮り直しを頼む仕組み(自動保存の差分で撮り直す等)を持たず、撮り直しが届かずに古いサムネイルが残ることが構造的に起きない。撮る引数(ffmpeg の品質やフィルタ)を変えたときは、キャッシュの形式の版を上げて、全部を別のファイル名にする。版を上げる前のファイル(版の印の番号が今の版より小さいものと、版の印の無い版3以前のもの)は、次にサムネイルを置いたときの刈り込みで、容量の上限を待たずに消す。今の版より大きい番号の印のファイルは残す(8節)。版を上げた後は全部の撮り方を撮り直すので、最初の1枚を置いた時点で古い版のファイルは無くなる
- **容量**: キャッシュの容量の上限は 50MB(50,000,000バイト)にする。1枚置くたびに、フォルダの jpg の合計が上限を超えていれば、使った時刻の古いものから消す。使った時刻とはファイルの更新日時のことであり、読んだときにも今の時刻へ進める。1枚は数KBなので、約1万件を持てる
- **書き込み**: `<要約値>.<プロセスの番号>.tmp` へ書いてから置き換える。2つのアプリが同じ撮り方を同時に撮っても、書きかけのファイルを取り合わない。落ちたアプリが残した書きかけのファイルは、刈り込みのときに10分より古いものを消す
- **壊れたキャッシュ**: 読んだ JPEG を画素へ戻せなければ、そのファイルを消して撮り直す。撮り直した画像も戻せなければ「撮れない」にする(撮り直しを繰り返さないため)。中身が空のファイルは無いとみなして消す
- **キャッシュの読み書きの失敗**: キャッシュは捨ててよいデータなので、読み書きできなくても一覧の表示を止めない。読めなければ撮り、書けなければ撮った画像を RAM に持って見せる。この失敗は画面に出さない(見せる結果が変わらないため)。環境変数 LOCALAPPDATA が無いときはキャッシュを使わずに撮る
- **層**: キャッシュの置き場所の管理と読み書きは、新しいクレート `thumbnail_cache` が持つ。`clip_domain` と std::fs だけを知り、egui も FFmpeg も `clip_library` も知らない。ライブラリ(`clip_library`)はサムネイルを知らず、スタックの削除と複製はサムネイルに触れない(削除したスタックのサムネイルは、容量の上限の刈り込みがいずれ消す)
- **作り方**: `video_source` の `動画の読み手::サムネイルを作る` が、先に ffprobe で動画の情報(コマの速さと読む映像の流れ)を調べ、再生と同じ規則(`アーキテクチャ.md` 1-10 の `コマを読む位置`)で開始の時刻を含むコマを選ぶ。`-ss <そのコマの半コマ手前> -i <動画> -map 0:<映像の流れ> -frames:v 1 -vf <コマをそろえる fps フィルタ>,crop=…,scale=w=192:h=108:force_original_aspect_ratio=decrease,format=yuvj420p|yuvj422p|yuvj444p` で ffmpeg に JPEG(`-q:v 8`)を作らせ、標準出力で受け取る。最後の `format` は JPEG の符号化器へ渡す画素の形式を全範囲の YUV に限る。限らないと、FFmpeg 9 は時刻が動画の終わりより後ろでコマが1つも来ないときに異常終了し、「コマが無い」と区別できなくなるためである(コマがあるときの画像は限らないときと同じである)。再生と規則を揃えるのは、開始の時刻がコマの途中にあるときに、再生で映すコマの次のコマを撮らないためである。クロップは百分率を元の寸法への割合の式(`iw*幅` 等)で渡す。左端+幅が100を超えるクロップ範囲は、はみ出さないよう左端と上端を寄せる
- **FFmpeg の期限**: 1枚の撮影で起動する ffprobe には動画を開くときと同じ30秒、ffmpeg には10秒の期限を置く(撮る処理は裏のスレッドで行うため、画面は止まらない)。動画の情報は、撮る裏のスレッドが動画のパスごとに覚えて使い回し、ファイルの大きさか最後に書き換えた日時が変わったときだけ調べ直す(`撮影に使う動画の情報の覚え`)。同じ動画から作ったスタックが多くても、同じ動画を件数分だけ調べ直さないためである。子プロセスを起動した後、10ミリ秒ごとに終わったかを見回り、期限を過ぎたら止めて(kill)「撮れない(時間切れ)」にする。固まった ffmpeg が撮影の全体を止めないためである。アプリを閉じるときは撮影を取り消し、見回りが気づいた時点で ffmpeg を止める。閉じるときに撮影の終わりを待つのは約10ミリ秒である
- **撮るとき**: 起動しただけでは撮らない。ライブラリの構えを開いている間だけ、見えている行から先にキャッシュを見て、無ければ撮る。見えている行を終えたら、残りの行を見せる順に撮っておく(スクロールした先で待たないため)。見えている行は、SengenEgui の仮想縦スクロールが描画のたびに組んだ行の範囲を応答として発し(`.見えている行を発する()`)、応答の適用が状態へ置き、次のフレームで状態が取り出して使う(画面は状態を書き換えない)。撮る仕事は1本の裏のスレッドへ1件ずつ頼み、次に撮るものはそのたびに画面のスレッドが選び直す。このため、登録したばかりのスタックもスクロールした先の行も、見えていれば待ち行列の後ろで待たない
- **読むとき**: キャッシュを見る仕事と JPEG を画素へ戻す仕事は、撮る仕事と別の1本の裏のスレッドが行い、同時に8件まで頼む。撮っている間(1枚あたり ffprobe と ffmpeg の2回の起動。1920×1080・2秒ごとのキーフレームの mp4 をこの開発機で測ると、ffprobe が約0.05秒、ffmpeg が約0.1〜0.25秒だった)も、キャッシュにあるサムネイルを待たずに出すためである。キャッシュを見るのは、ライブラリの構えを開いている間の、見えている行と残りの行である。画素へ戻すのは見えている行だけである
- **GPU**: RAM には JPEG のバイト列(1枚 数KB)だけを全件分持つ。画素へ戻してテクスチャにするのは見えている行だけであり、テクスチャが48枚を超えたら、見えていないものを最後に見えた時の古い順に捨てる(JPEG のバイト列は残す)。1枚は 192×108×4 = 約83KB なので、GPU のメモリは件数に比例せず、約4MB にとどまる(見えている行がそれより多い大きなウインドウでは、見えている行の分だけ持つ)
- **描き直し**: 裏のスレッドの返事を待っている間は、入力が無くても0.1秒ごとに描き直して結果を受け取る。見えている行のサムネイルがまだ出せない間と、ライブラリの構えで見せる行(絞り込みの後の行)にキャッシュを見る前の行が残っている間は、約60回/秒で描き直す(絞り込みで隠れた行はキャッシュを見る仕事が回らないため数えない。数えると描き直しが止まらない)(キャッシュを見る仕事はフレームごとに最大8件まで頼むため、0.1秒ごとでは400件の一覧のキャッシュを見終えるのに約5秒かかる)。裏のスレッドが異常終了したら、返事を待っていた行を「撮れない(裏のスレッドが止まっている)」にして、返事を待つのをやめる(描き直しを永久に続けないため)
- **一覧での表示**: 行の左に 96×54 論理画素の枠を置き、見せられるサムネイルは縦横比を保って収める。読んでいる・撮る順番を待っている・撮っている・撮らない(動画が見つからない・再生できるクリップが無い・FFmpeg が無い)は枠の中に短い文で、撮れないは「撮れない」と出して理由を枠に乗せたときの説明に出す。動画が見つからなくても、キャッシュにあれば見せる
- **JPEG を画素へ戻す方法**: image クレート(`jpeg` の機能だけ)で戻す。ffmpeg で rawvideo の RGBA へ変換する方法は、1枚ごとにプロセスを起動するため1枚あたり数十ミリ秒かかり、数百件で数秒から十数秒になる。image クレートは同じプロセスの中で1枚1ミリ秒未満で戻す。image は eframe(arboard)が既に依存の木に入れている版と同じ 0.25 であり、足す重さは jpeg の復号器(zune-jpeg)だけである
- **錠**: キャッシュはライブラリの外にあり、書きかけのファイルの名前をプロセスごとに分けるため、読み取り専用のアプリ(判断9)もキャッシュを見て撮る
- **以前の置き方の片付け**: 以前の版は、サムネイルをライブラリのフォルダの `<識別子>.jpg` に置いていた。書けるアプリは、一覧を作る前に、ライブラリのフォルダの `*.jpg` と `*.jpg.tmp` を消す。ライブラリのフォルダにはスタックのファイルと錠のファイルだけを残す。消せなかったファイルは、次に一覧を作るときに消し直す(拡張子が json でないため、一覧には出ない)

## 4. この段階でやらないこと

- **フォルダ分けやタグ**: 絞り込みは名前だけにする
- **別の計算機との同期**: 置き場所はこの計算機のアプリのデータのフォルダだけである。動画のパスが計算機ごとに違うため、同期は動画の場所の指定し直しと組にして別に決める
- **削除の取り消し**: 削除は確認のダイアログで確かめ、ファイルを消す(ごみ箱へは送らない)

## 5. 既知の制約

直さずに受け入れている振る舞いを記録する。どれも保存したファイルを壊さない。

- **走査の途中の一時的な「読めない」行**: 走査のスレッドと書き込みのスレッドは別々に動く。走査がファイルを読む瞬間に書き込みのスレッドが同じファイルを
  置き換えていると、そのファイルが一覧に「読めない(理由)」の行として出ることがある。ファイルは壊れておらず、次に一覧を読み直すと通常の行に戻る
- **閉じるときは溜まった走査も待つ**: `裏で動くライブラリ` を落とすと、書き込みのスレッドが受けた頼みを終えた後、走査のスレッドも受けた走査を終えるまで待つ。
  一覧の読み直しを続けて頼んだ直後に閉じると、遅いドライブではその分だけ閉じるのが遅れる
- **落ちた直後の錠の解放の遅れ**: アプリが落ちたときは OS が錠を解くが、解くまでの時間はそのときのシステムの資源の具合で決まる
  (Windows の LockFileEx の説明による)。落ちた直後に起動すると、錠がまだ解けておらず読み取り専用で開くことがある。少し待ってアプリを起動し直せば書ける
- **読み取り専用のアプリで開いたスタックは未登録になる**: 判断9 のとおり、読み取り専用で開いたスタックは未登録として開き、変更はライブラリへ保存しない。
  未登録の並びは自動保存の対象でないため、そのアプリで変えた並びを捨てる操作(閉じる等)の前には確かめるダイアログを出す。読み取り専用ではライブラリへ書けないため、
  ダイアログの [ライブラリに保存する] は押せず、残すには「JSON保存」で書き出す

## 6. settings.json の形式

アプリの設定(`%APPDATA%\ClipViewer\settings.json`)は、`clip_viewer` の `persistence/app_settings/` が読み書きする。
ライブラリと同じく、先に `format` と `version` だけを読んで版を判別し、版ごとの型から最新のアプリの設定へ変換する。

```json
{
  "format": "ClipViewer.settings",
  "version": 1,
  "ffmpegFolder": "C:\\ツール\\ffmpeg 7.1\\bin",
  "windowSize": {
    "width": 1440.0,
    "height": 810.0
  },
  "windowMaximized": true,
  "volume": 0.25,
  "playbackSpeed": 0.75,
  "mirrorHorizontally": true,
  "aspectRatio": "crop",
  "displaySize": "noMargin",
  "keyBindings": {
    "togglePlayback": [
      "P"
    ],
    "toggleTheater": [
      "Ctrl+Shift+T"
    ]
  }
}
```

第1版の項目は次のとおりである。どの項目も無くてよく、無い項目は既定の値として読む。

| 項目 | 意味 | 無いときと読めない値のとき |
|---|---|---|
| `ffmpegFolder` | FFmpeg を置いたフォルダ(画面の「保存して探し直す」で保存する) | 未設定 |
| `windowSize` | 最大化も全画面もしていないときのウインドウの中身の幅と高さ(論理画素) | 最初の大きさ(1200×620)。正の数でなければ同じ |
| `windowMaximized` | 最大化しているか | 最大化していない |
| `volume` | 音量のつまみの値(0〜1) | 0.5。範囲の外は0〜1へ収める |
| `playbackSpeed` | 再生の速度の倍率 | 1。速度のつまみの範囲(0.25〜2)の外は範囲の端へ収める |
| `mirrorHorizontally` | 出力を左右反転するか(`画面.md` 判断15) | 反転しない |
| `aspectRatio` | 出力のアスペクト比(`crop`・`16:9`・`4:3`・`1:1`・`9:16`) | クロップ枠に合わせる(`crop`。オーナーの決定。移植元の既定は16:9)。知らない表記も同じ |
| `displaySize` | 出力の表示サイズ(`standard`・`large`・`widthFirst`・`noMargin`) | 大きめ(`large`)。知らない表記も同じ |
| `keyBindings` | キーの割り当てのうち、既定と違う操作(`画面.md` 判断18)。操作の名前から、キーの組の表記の並び(1つか2つ)への対応 | すべて既定のキー。下の「keyBindings の読み方」 |

`windowSize` から `keyBindings` までを見る側の設定と呼ぶ(何を覚え、いつ書くかは `画面.md` 判断17)。見る側の設定は、1つも書いていないファイルでは項目ごと書かず、
一度書いたら `windowSize` から `displaySize` までの7つの項目をすべて書く。`keyBindings` は、既定と違う操作があるときだけ書き、その操作だけを並べる。文字列の項目の知らない表記は、ファイルを壊れているとはみなさず、その項目だけを既定の値として読む。新しいアプリが同じ版に表記を足しても、
古いアプリが FFmpeg の置き場所まで失わないためである(古いアプリは、見る側の設定を書くときにその項目を自分の知っている値で上書きする)。数と真偽の項目の型が違う
(`volume` が文字列である等)ファイルは、ほかの項目と同じく壊れているとみなす

- **keyBindings の読み方**: 操作の名前とキーの組の表記は `persistence/app_settings/v1_keys.rs` が決める(操作の名前は `togglePlayback`・`nextClipOrNotify`・`previousClip`・`nextClip`・
  `stepFrameBackward`・`stepFrameForward`・`skipBackward5Seconds`・`skipForward5Seconds`・`slowDown`・`speedUp`・`toggleMute`・`toggleTheater`・`leaveFullscreenOrTheater`・
  `toggleFullscreen`・`saveToLibrary`・`toggleKeyList`・`undo`・`redo`・`setStartToCurrentPosition`・`setEndToCurrentPosition`)。キーの組の表記は SengenEgui の `キーの組::表記` の形
  (「Ctrl+Shift+Z」「Shift+←」「Space」。修飾キーは Ctrl・Alt・Shift の順)である。知らない操作の名前の行と、読めない表記や1つか2つでない並びの行は、その行だけを無いものとして読む。
  行は名前の順に読み、読んだ行がほかの操作(ほかの行で変えた操作か、行の無い操作の既定のキー)とキーで重なれば、重なりに関わる行のうち後に読んだ行を1つずつ、重なりが無くなるまで無いものとして読む
  (`viewer_settings/keys/saved_changes.rs`)。全体を無いものとすると、重なりの無いほかの行で利用者が変えたキーまで知らせなしに既定へ戻るためである。
  後に読んだ行を捨てるのは、行の順が名前の順で決まり、どの行を捨てたかが毎回同じになるためである。入れ替えた2つの行のように、そろって読めば重ならない行は両方を生かす。無いものとした行はどれも既定のキーになり、ファイルを壊れているとはみなさない(新しいアプリが同じ版に操作を足しても、
  古いアプリが FFmpeg の置き場所まで失わないため)。古いアプリは、知らない操作の行を持ち回らない(見る側の設定を書くときに、自分の知っている操作だけで `keyBindings` を書き直す)。
  `keyBindings` がオブジェクトでないか、行の値が文字列の配列でないファイルは、ほかの項目の型が違うときと同じく壊れているとみなす
- **第0版**: 版を持たなかった最初の形(`{"ffmpegFolder": "..."}`)である。`format` と `version` の両方が無いファイルを第0版として読み、
  次に保存するときに第1版で書く。第0版は v0.1.0 より前のアプリが既に書いているため、読み手を消さない
- **第1版は知らない項目を許す。** 同じ版の中で知らない項目は `その他` として持ち回り、書くときに戻す。ライブラリのスタックのファイルと
  方針が違うのは、設定はウインドウの大きさ・音量のように項目が少しずつ増え、項目を足すたびに版を上げると、古いアプリがその設定を読めなくなって
  FFmpeg の場所まで失うためである。持ち回れば、古いアプリは新しい項目を読まずに残せる。スタックのファイルは項目がクリップの意味を変えうるため、
  知らないまま持ち回って自動保存すると中身の食い違いを作る。このため版を上げて古いアプリに読ませない
- **同じ版に項目を足す書き方**: `v1.rs` の `第1版の設定` に `Option` の項目として足し(見る側の設定の項目は、`v1_viewer.rs` の `第1版の見る側の設定` へ足す。この型は第1版の設定へ平らに入れてある)、`#[serde(default, skip_serializing_if = "Option::is_none")]` を付ける。
  値が無いときに書かないため、第1版の見本の書き出しが変わらない。最新の `アプリの設定`(`settings.rs`)にも同じ項目を足す。変換は `..` を使わずに
  分解・組み立てるため、片方だけ足すとコンパイルが通らない。意味を変える変更・名前の変更・項目の削除は、同じ版の中でしてはならず、版を上げる
- **このアプリの知らない書き手のファイルは書き換えない。** 新しすぎる版(「新しい ClipViewer で保存された。更新すれば読める」)・知らない形式の名前・
  読めない版の番号のファイルは、起動時に通知で理由を知らせ、FFmpeg の場所の保存でも書き換えずに失敗を返す。利用者の手で直せる情報(パスと理由)を文に含める
- **壊れたファイルは移してから書き直す。** JSON として読めないか形が不正なファイルは、起動時に通知で理由を知らせる。知らせの文には、ファイルのパスと、
  「このファイルを消すか直せば、次の起動から読める」と、「FFmpeg の置き場所を保存するときには、このファイルを別の名前へ移して書き直す」を入れる。
  設定を保存する口は、今は FFmpeg が見つからないときの「保存して探し直す」だけであり、FFmpeg が PATH にある利用者には保存の時が来ないためである。
  保存するときは、アプリはそのファイルを `settings.json.broken-<年月日>-<時分秒>-<プロセスの番号>`(日時はこの計算機の時間帯)へ移し、
  何も設定していない状態に保存する項目だけを足して第1版で書く。その名前が既にあれば、末尾に `-2` から順に番号を足した、まだ無い名前へ移す。
  移す直前に、アプリはもう一度読み直し、まだ壊れているときだけ移す。2つのアプリがほぼ同時に保存したときに、先に移した写しを上書きせず、
  もう一方のアプリが書いたばかりの正しいファイルを移さないためである。アプリは、移したことと移し先を保存の知らせで伝え、移した後で書けなかったときも
  失敗の文に移し先を入れる。以前の版は `std::fs::write` で直接書いていたため、途中で落ちると壊れたファイルが残る。
  壊れたファイルを書き換えないままにすると、FFmpeg の場所を二度と保存できないためである
- **見る側の設定の保存は、壊れたファイルを移さない。** 見る側の設定(ウインドウの大きさ・音量など)は、変えてから落ち着いたときとアプリを閉じるときに自動で書く。
  利用者の操作なしに壊れたファイルを移すと、知らせの文(「FFmpeg の置き場所を保存するときには、このファイルを別の名前へ移して書き直す」)と食い違うため、
  壊れたファイルと書き換えてはならないファイルには書かず、最初の1回だけ通知で理由を知らせる。壊れたファイルを移して書き直すのは、FFmpeg の置き場所の保存だけである
- **保存の手順**: 今のファイルを読み直す → 変える項目だけを変える → `settings.json.<プロセスの番号>.tmp` へ書いて `sync_all` で記憶装置まで書き切る
  → `rename` で置き換える。読み直すのは、ほかの項目(知らない項目を含む)を消さないためである。書きかけで落ちても元のファイルは壊れない。
  settings.json はライブラリの錠の外にあり、2つのアプリが同時に保存しうるため、書きかけの名前をプロセスごとに分ける。
  ただし、見る側の設定を自動で書くのはライブラリの錠を持つアプリだけである(`画面.md` 判断17)。読み取り専用で起動した2つ目のアプリが書くのは、利用者が画面で行う FFmpeg の置き場所の保存だけである
- **既知の制限: ほぼ同時の保存で一方の変更が消えうる。** 読み直してから置き換えるまでの間に、もう一方のアプリが書くと、後から置き換えた側がもう一方の変更を消す。
  書き合うのは、1つ目のアプリの見る側の設定の保存と、2つ目のアプリの FFmpeg の置き場所の保存が、ほぼ同時に起きたときだけである。settings.json は錠の外にあり、
  ファイルの錠で書き合いを防ぐ仕組みは入れていない。消えた変更は、FFmpeg の置き場所なら保存し直せば戻り、見る側の設定なら次に値を変えたときに書き直す
- **第0版の同じ名前の項目。** 第0版のファイルに第1版が書く項目と同じ名前の項目(`volume` 等)があれば、第0版には意味が無いため、読むときに捨てる。
  知らない項目として持ち回ると、第1版で書くときに同じ名前の項目が2回出るためである。第1版が書く項目の名前の一覧は `v1.rs` の `第1版が書く項目の名前` である

## 7. 形式の版を上げる手順

スタックのファイル(`ClipViewer.library`)と重ね合わせのファイル(`ClipViewer.overlay`。新しい版の型は `clip_domain/src/library/overlay_v2.rs`、版を選ぶ `match` は `overlay_format.rs`)と settings.json(`ClipViewer.settings`)は同じ手順で版を上げる。settings.json は項目を足すだけなら版を上げない(6節)。

1. 新しい版の型を足す(ライブラリは `clip_domain/src/library/v2.rs`、settings.json は `clip_viewer/src/persistence/app_settings/v2.rs`)。
   ライブラリの型には `deny_unknown_fields` を付ける
2. 新しい版の型と最新の型の両方向の変換を書く。最新の型は `..` を使わずに分解・組み立てる
3. `format.rs` の版を選ぶ `match` に新しい版の枝を足し、最新の版の番号(`最新の版の番号`)を新しい版にする
4. 書き出しを新しい版の型へ切り替え、古い版の書き手(`最新から作る`)を消す。古い版は二度と書かない
5. **古い版の読み手と見本(`tests/fixtures/library_v1.json`・`tests/fixtures/overlay_v1.json`・`app_settings/fixtures/settings_v1.json`)は永久に残す。** 見本は書き換えない。
   見本を読んだ結果を手で組んだ期待値と比べる試験は残し、書き出しが見本と1バイトも違わないことを比べる試験は、新しい版の見本と比べる試験へ移す
   (古い版の見本は、もう最新の書き出しとは一致しないため)。新しい版の見本を同じ規則で置く
6. **古い版のファイルを初めて書き換える前の控えをどうするかを決める。** 新しい版で書くと、古いアプリはそのファイルを読めなくなる。
   版を上げる変更の中で、控えを取るか(取るなら置き場所と、いつ消すか)を決めて本文書に書く。控えはライブラリのフォルダの直下に置かず、
   サブフォルダにだけ置く(8節「互換の約束」。例: `library\backup-v1\<識別子>.json`)
7. 本文書の判断4(または6節)の形式の例と、互換の約束が変わらないことを確かめる

## 8. 互換の約束

公開した版のアプリが読み書きする置き場所と名前は、次の版以降も変えない。変えると、古いアプリと新しいアプリが同じ計算機で別々のデータを見る、
または錠を取り合わずに同じライブラリを書き合うためである。

- アプリのデータの置き場所は `%APPDATA%\ClipViewer` であり、ライブラリのフォルダはその下の `library` である。名前を変えない
- 錠のファイルの名前は `ClipViewer.lock` であり、置き場所はライブラリのフォルダの直下である。名前と置き場所を変えない(判断9)
- 重ね合わせのフォルダの名前は `overlays` であり、置き場所はライブラリのフォルダの直下である。名前と置き場所を変えない。`overlays` の中の名前の規則は、スタックのファイルと同じく `<重ね合わせの識別子>.json` と書きかけの `<重ね合わせの識別子>.json.tmp` であり、錠のファイルは `ClipViewer.lock` である(`同時再生.md` 4-4)
- ライブラリのフォルダの直下には、スタックのファイル(`<スタックの識別子>.json`)とその書きかけと錠のファイルのほかに、新しいデータを置かない。
  新しいデータはサブフォルダにだけ置く。走査はサブフォルダの中を読まないため、古いアプリもサブフォルダのデータを読めない行として出さない
- 将来の版は、ライブラリのフォルダの直下で次の名前を使ってはならない。今の版の書けるアプリが、走査の前の片付けで消すためである。
  `*.jpg` と `*.jpg.tmp`(以前の版のサムネイルとして消す)、`*.json.tmp`(対応する `*.json` が無く1日より古ければ、置き去りの書きかけとして消す)
- settings.json の置き場所とファイル名(`%APPDATA%\ClipViewer\settings.json`)を変えない。壊れたファイルの移し先の名前(`settings.json.broken-*`)と
  書きかけの名前(`settings.json.*.tmp`)を、ほかの用途に使わない
- settings.json の見出しの形を変えない。`format` は文字列、`version` は0以上の整数である。今の版は見出しを先に読んで版を判別し、
  見出しの形が違うファイル(`version` が文字列や小数である等)を「壊れている」と見て、FFmpeg の置き場所を保存するときに別の名前へ移すためである。
  版を上げるときも、見出しの形はそのままにして `version` の数だけを大きくする
- 起動の受け口の案内(`%APPDATA%\ClipViewer\launch.json`)の置き場所とファイル名と、項目 `port`(受け口のポートの番号)と `passphrase`(合言葉)の名前と意味を変えない。
  後から起動したアプリがこの案内を読み、先に起動していたアプリへ受け渡しの本文を送るため、違う版のアプリどうしが読み合う
- 受け渡しの本文(`clip_viewer` の `launch/wire.rs`。1行の JSON)について、項目 `passphrase` と `request`、頼みの `kind` の値 `focus` と `open`、
  `open` の項目 `path` と `skipped` の名前と意味を変えない。変えてよいのは項目を足すことだけである。読む側は知らない項目を無視する
  (`launch/guide.rs` と `launch/wire.rs` の型は `deny_unknown_fields` を付けていないことを確かめた)。ただし、読む側は知らない `kind` の値を

- サムネイルのキャッシュの置き場所(`%LOCALAPPDATA%\ClipViewer	humbnails\`)を変えない。ファイル名の形 `<要約値の16進数32文字>.v<キャッシュの形式の版の番号>.jpg` と、
  書きかけの名前の形 `<要約値>.<プロセスの番号>.tmp` を変えない(判断10)。版を上げるときは、`v` の後ろの番号だけを大きくする

  容量の上限を超えた分の今の版の画像だけである。今の版より大きい番号の印の画像は、数えも消しもしない。新しい版のアプリと行き来する利用者や、
  2つの版を同時に動かす利用者で、互いのキャッシュを消し合わないためである(このため、2つの版の画像の合計は、上限の2倍まで増えうる)
